## 1. 이 프로젝트가 무엇인가

AI가 쓴 한글을 "사람이 쓴 글처럼" 윤문하는 Claude Code 스킬. 10대 카테고리 70여 개
"AI 티" 패턴을 탐지·분류해 **내용은 건드리지 않고 문체만** 재작성한다.

우리와 겹치는 지점: 우리 앱도 **LLM이 한국어 산문을 생성**한다 — 위키 페이지 본문,
`summary` 필드, 질의 답변, `synthesis/` 페이지. 그 출력이 "AI가 쓴 티"가 나면
업무 문서로서 신뢰를 잃는다.

겹치지 않는 지점: 저쪽은 **사후 윤문 도구**, 우리는 **생성 시스템**. 그래서 같은 규칙을
써도 적용 지점이 다르다 (§6).

## 2. 방법론이 단단하다

graphify 검토 때와 달리 이쪽은 **자체 대조 코퍼스로 실측하고 한계를 명시**했다.

- **AI 코퍼스**: 동일 주제 20개를 Fable 5 / GPT-5.6-sol / Haiku 4.5에 던져 만든 60편.
  세 모델을 쓴 이유를 "한 모델의 습관을 AI다움으로 오인하지 않기 위해"라고 밝힘
- **인간 코퍼스**: **2022-01-01 이전** 발행이 확인된 한국어 산문 60편(ChatGPT 공개 이전 =
  AI 혼입 없음). Wayback Machine으로 발행일 이중 확인
- **검정**: 로그우도비 G² (Dunning 1993)
- **한계를 스스로 4가지 적음**: 인간 코퍼스가 편집된 전문 산문이라 격차가 과장될 수 있음
  (개인 블로그 서브셋에서 장문 격차 113.5→27.7로 줄어듦), 주제 미짝지음, 표본 60편,
  번역 맥락 미검정

**기각 기록도 있다.** "GPT-5.6-sol에게 이 패턴이 여전히 AI 티인 이유를 최대한 강하게
변호하라고 시킨 뒤, 그 변호가 데이터를 이기지 못한 것만 기각으로 기록"한다.
자기 규칙을 반증하려 한 흔적이 있다.

또 하나 인용할 만한 대목 — 자기가 인용하던 근거를 스스로 정정했다:

> taxonomy가 인용하던 김정우(2007)는 계량 연구가 아니라 유형론·처방 논문이다.
> "유형론적 근거"로만 유효하며 "실증 근거"로 인용하면 과잉 귀속.

## 3. 가져온 것

### 3.1 확증된 패턴 (사람 대비 AI 과다, 구조·기능 층위)

| 패턴 | AI/1k | 인간/1k | 배수 | G² |
|---|---|---|---|---|
| 부정 대구 `A가 아니라 B` | 5.8 | 0.6 | **9.2×** | 41.7 |
| 쉼표 과다 | 49.1 | 33.4 | 1.5× | 25.5 |
| 쉼표 포함 문장 비율 | 394.8 | 285.5 | 1.4× | 13.3 |
| `~한다` 종결 편중 | 95.0 | 52.2 | 1.8× | 9.5 |

### 3.2 "AI가 못 쓰는 것"도 신호다

과다만 보던 시각을 뒤집는 관찰이다.

| 결핍 | AI/1k | 인간/1k | G² | 처방 가능? |
|---|---|---|---|---|
| **장문**(100자+ 문장) | 8.1 | 91.3 | 60.9 | ✅ 인접 문장 잇기 |
| 직접 인용 | 0.0 | 8.7 | 96.4 | ❌ 없는 인용을 지어내면 안 됨 |
| 괄호 | 1.2 | 10.6 | 69.5 | ❌ 관측만 |

**"처방 가능한 것만 규칙화하고 나머지는 관측만 한다"** — 없는 것을 만들어내는 처방은
의미 드리프트를 유발하므로 금지. 이 원칙을 그대로 채택했다.
우리 Lint에서 장문 결핍(E-1)만 처방으로, 인용·괄호 결핍은 넣지 않았다.

### 3.3 채택하지 않은 것 — z-score

`metrics_v2.py`는 15개 지표의 z-score를 내지만, `baseline_v2.json`이 이렇게 적혀 있다:

```json
"source": "Placeholder. ... 정밀 측정은 별도 calibration 회차에서 수행.",
"calibration_due": true,
"_placeholder": true   // 모든 셀
```

우리 M0 산출물을 실제로 넣어 봤더니 `v2_baseline_warnings` 14건 — **전 지표가 미보정**.
따라서 z-score와 `risk_band`는 쓰지 않고, **결정론적 패턴 규칙만** 가져왔다.

## 4. 우리 탐지기 — 검증 결과

`spikes/korean/detect.mjs`. quick-rules를 TS/JS로 이식하되, **우리 위키 구조에 맞게
보호 구역을 추가**했다. 24개 규칙(S1 14 / S2 10).

### 4.1 보호 구역 마스킹 — 이게 핵심이다

우리 위키 페이지에는 절대 건드리면 안 되는 것들이 있다.

```
front-matter / 앵커 인용 [^src-kickoff#slide-12] / wikilink [[...]]
/ 표 / 코드블록 / 헤딩 / URL
```

이 구간을 오프셋을 보존한 채 공백으로 치환한 뒤 탐지한다.

```
OK   마스킹: "id: ent-acme"
OK   마스킹: "[^src-kickoff"
OK   마스킹: "[[concepts/"
OK   마스킹: "| 결론적으로 |"
OK   마스킹: "코드다"            (코드블록 안)
OK   본문 산문은 남음: "주 협력사가 아니라"
→ 5/5 마스킹, 본문 보존 PASS
```

front-matter의 `summary`에 "결론적으로 중요한 것은…"이 들어 있어도 세지 않는다.
`summary`는 index.md 조립용 메타데이터이지 산문이 아니기 때문이다.

### 4.2 정답을 아는 문장으로 검증

각 규칙마다 **반드시 잡아야 할 문장(POS)** 과 **잡으면 오탐인 문장(NEG)** 을 심었다.
NEG는 업무 위키에 정상적으로 나오는 한국어로 골랐다.

```
TP=24 FN=0 FP=0 TN=30
정밀도 1.000 · 재현율 1.000 · 오탐 0건
```

### 4.3 ★ 한국어 정규식 함정 3가지

전부 검증에서 **실제로 놓치거나 오탐이 나서** 발견했다. 추측이 아니다.

**① `\b`는 한글 경계에서 동작하지 않는다.**
`(?:이다|다)\b`로 썼더니 "핵심은 구매팀의 최종 검토다."를 놓쳤다.
→ 문장 종결 앵커 `[.\n]`로 교체.

**② 조사 이형태 — 받침 유무로 은/는이 갈린다.**
`(?:문제|핵심|차이)은`으로 썼더니 `문제`**`는`**, `차이`**`는`** 을 전부 놓쳤다.
받침 있는 `핵심은`만 잡혔다. → `(?:은|는)` 둘 다 받는다.

**③ 분열문의 서술부는 연결어미 없이 바로 종결된다.**
`[^.\n]{1,40}`로 span을 잡았더니
"이유는 아직 확인되지 않았**으므로** 구매팀에 문의한다."를 오탐했다.
절 경계를 넘어간 것이다. → span 안에 연결어미(`으므로|지만|는데|면서|…`)가 오면
매칭하지 않도록 부정 전방탐색을 넣었다.

세 함정 모두 **라틴 문자 기준 정규식 습관에서 온다.** M0의 Jaro-Winkler 임계 문제와
같은 계열이다 — 차용한 것을 한국어에서 반드시 재검증해야 한다.

## 5. A/B — 규칙 주입이 실제로 개선하는가

### 측정

동일 질문·동일 근거·동일 모델(`claude-sonnet-5`)로 우리 질의 답변 형태의 한국어 산문을
생성했다. B는 같은 세션을 재개해 quick-rules 본문(약 10KB)을 주입하고 다시 쓰게 했다.

```
A 규칙 없이          등급 C  S1=1  S2=0  (705자)
B quick-rules 주입   등급 C  S1=2  S2=0  (588자)

패턴별 (A → B)
  C-11  S1  연결어미 뒤 쉼표   1 → 2   ★악화
```

### ★ 역주입을 재현했다

B가 늘린 C-11은 오탐이 아니다. 실제 매치를 확인했다.

```
A: "...확정된 계약 조건이 아니며, 구매팀의 최종 검토와..."
B: "...슬라이드에는 기존 일정이 그대로 실렸고, 두 문서 사이에..."   ← 새로 생김
   "...확정된 계약 조건이 아니며, 구매팀의 최종 검토와..."
```

im-not-ai의 quick-rules에 이런 경고가 있다:

> **윤문이 새 연결어미 쉼표를 만들지 말 것 — 윤문 후 개수가 원문보다 늘면 실패**
> (역주입 실측 2/28편)

우리는 **1/1로 재현**했다. 규칙을 읽은 모델이 문장을 다시 쓰면서 그 규칙이 금지한 패턴을
새로 만들어 넣었다.

### 정직한 결론

**규칙 주입이 출력을 개선한다고 말할 근거가 지금은 없다.**

- 표본 1건이다. 통계가 아니라 일화다
- 육안으로는 개선이 보였다(A의 "다르게 적혀 있는 것은 ~때문이다" 분열문이
  B에서 "다르게 적힌 이유는 ~어서다"로 바뀜). 그러나 **우리 탐지기가 그 형태를 아직
  커버하지 않아** 수치로 잡히지 않았다 — 즉 탐지기도 아직 불완전하다
- 확실한 것은 하나: **다시 쓰게 하면 새 패턴이 주입될 수 있다**

그래서 규칙 주입은 채택하되, 계획서에 **"개선 효과 미검증"** 으로 명시하고
M2에서 표본 20건 이상으로 재측정하는 항목을 남긴다.

## 6. 왜 윤문 패스를 v1에서 뺐는가

im-not-ai 자체는 잘 만들어졌지만, **우리 시스템에 그대로 붙이면 세 가지가 충돌**한다.

**① 우리 페이지는 산문이 아니라 구조체다.**
M0에서 우리 CLI가 만든 실제 위키 페이지를 저쪽 채점기에 넣었더니 `risk_band: low`가
나왔다. 좋아서가 아니라 **글이 짧고 목록 위주라 신호가 잡히지 않아서**다.
humanize-korean은 400~900자 이상의 흐르는 산문을 전제한다.

**② 앵커 인용·주장·front-matter가 위험해진다.**
우리 설계의 핵심은 "모든 주장에 앵커 인용"이다. 문체 재작성은 문장을 합치고 나누는데,
그 과정에서 인용이 어느 주장에 붙어 있었는지가 흐트러진다. 보호 구역 마스킹은
**탐지**에는 충분하지만 **재작성**에는 부족하다.

**③ 우리 원칙과 어긋난다.**
"LLM은 디스크에 직접 쓰지 않는다 — 사람이 diff로 승인한다." 문체 윤문은 문서 전체에
걸친 큰 diff를 만든다. 검토자가 "내용이 안 바뀌었는지" 확인하기가 오히려 어려워진다.
im-not-ai가 변경률 30%/50% 게이트를 둔 이유가 이것이고, 우리는 그 게이트를 또 만들기보다
**애초에 재작성을 하지 않는 쪽**을 택한다.

**대신 이렇게 한다:**

```
생성 시    schema/AGENTS.md의 작문 규칙   (예방 — 효과 미검증)
저장 전    Lint #11 탐지 → 사람에게 표시   (검출 — 검증 완료, 오탐 0)
수정       사람이 고르고 앱이 적용         (기존 diff 승인 흐름 그대로)
```

윤문 패스는 v2로 미룬다. 그때는 문단 단위 국소 패치로, 앵커가 붙은 문장은 제외하고,
before/after 게이트(C-11 개수가 늘면 롤백)를 반드시 건다.
