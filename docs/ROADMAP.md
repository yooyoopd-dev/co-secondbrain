## 3. 사내 문서는 반출하지 않는다 — 수치만 회수한다

17 · 18 의 원래 계획은 사내 문서와 엔티티명 목록을 개발 쪽으로 가져오는 것이었는데 반출이 불가하므로 **스크립트가 사내 PC 에서 돌고 사람이 화면에 뜬 집계 수치만 옮겨 적는 방식**으로 바꾼다. 검증에는 개수와 분포면 충분하다.

### 3.1 지켜야 할 것

- 스크립트는 **원문 텍스트 · 파일명 · 엔티티명을 출력하지 않는다.** 개수와 분포만 낸다
- 출력은 한 화면에 들어가는 표 하나여야 한다. 사람이 눈으로 확인하고 옮겨 적는다
- 파일을 만들지 않는다. 표준 출력으로만 낸다. 실수로 딸려 나갈 파일 자체를 안 만든다
- 실패한 파일은 **사유의 종류별 건수**만 센다. 사유 문자열에 경로가 섞이면 지운다

### 3.2 17번 — 추출기 자가검사가 낼 수치

| 항목 | 형태 |
|---|---|
| 확장자별 파일 수 · 성공 · 실패 | 정수 |
| 실패 사유 종류별 건수 | 사유 분류명 + 정수 |
| 파일당 조각 수 · 앵커 수 | 최소 · 중앙값 · 최대 |

| `.msg` 파싱 성공률 · xlsx 수식 셀 참조 추출 건수 | 정수 |

### 3.3 18번 — 엔티티 유사도 자가검사가 낼 수치

| 항목 | 형태 |
|---|---|
| 이름 개수 · 비교한 쌍 수 | 정수 |

### 8.1 0% 는 Gemini 가 못 맞춘 것이 아니다

ENOENT 하나가 전부를 설명한다. **npm 전역 설치는 확장자 없는 껍데기를 같이 깐다** —
`gemini` · `gemini.cmd` · `gemini.ps1` 이 한 폴더에 있고 `where` 는 확장자 없는 것을 먼저
준다. 그것은 sh 스크립트라 Windows 의 CreateProcess 가 못 읽는다. `record.mjs` 의
`resolveBin` 이 `[0]` 을 그냥 집었다. `gemini-schema-check.mjs` 는 `execFile('gemini', ...)`
를 그대로 불렀다. 후자는 try/catch 가 ENOENT 를 빈 응답으로 삼켜서 **파싱 실패 10 으로
기록됐다.**

claude-code 가 통과한 것은 `where claude` 의 첫 실행 후보가 띄울 수 있는 형태였다는
뜻이다. 어떤 확장자였는지는 회수한 수치에 없어서 **확실하지 않다.**

그러므로 **W3 의 n 은 여전히 3 이다** (§1 의 회수본). 이번 실행은 Gemini 의 스키마
안정성을 재지 못했다.

### 8.2 제품 코드도 같은 결함을 갖고 있었다

`core/agent/exec.ts` 가 `spawn(bin, ...)` 을 shell 없이 불렀다. **배포한 exe 로도 사내 PC
에서 Gemini 를 못 띄웠을 것이다.** 설정 화면에는 "이 PC 에서 못 찾았습니다" 로만 보였을
것이라 원인을 짐작하기 어려웠다.

`pickWindowsBin` 을 넣어 `.exe` · `.com` 을 먼저, 없으면 `.cmd` · `.bat` 을 고른다.
`.cmd` 는 cmd.exe 를 거쳐야 하는데 거기서는 Node 가 `" ^ & | < > %` 를 다 지켜 주지
못한다. claude-code 는 스키마 JSON 을 argv 로 넘기므로 그런 인자가 섞이면 **조용히 깨지는
대신 거절한다.** 못 맞춘 결과를 모델 탓으로 읽는 것보다 안 도는 편이 낫다.

리눅스에서도 도는 순수 함수라 `app/test/agent.test.ts` 가 4건으로 잠근다.

### 8.3 다음 왕복에서 다시 재야 할 것

- `node spikes/cli/record.mjs --only gemini` — 이번 수정으로 Gemini 가 뜨는지
- 뜨면 `node spikes/cli/gemini-schema-check.mjs 10` — W3 를 n=10 으로 다시
- `where claude` 와 `where gemini` 의 출력 그대로 (경로는 사용자명을 지우고)

### 8.4 2회차 — Gemini 는 떴다. W3 는 또 못 쟀다

같은 날 수정본으로 다시 돌렸다.

| 설치 | `C:\Users\...\AppData\Roaming\npm` · `@google/gemini-cli@0.58.0` |

**해석이 갈린다.** `record.mjs` 가 통과했으므로 Gemini 는 뜬다. 실행 파일 고르기는
고쳐졌다. 그런데 `gemini-schema-check.mjs` 는 그대로 0% 다. 두 스크립트가 다른 것은

따옴표·백틱이 들어 있어 명령줄에서 통째로 깨진다. **cmd.exe 는 줄바꿈이 든 인자를

(프롬프트는 stdin 으로 넘긴다) 이 스파이크만 옛 방식으로 남아 있었다.

프롬프트를 stdin 으로 옮기고 인자를 `record.mjs` 와 같은 조합으로 맞췄다.

| 1,500장 | 263만~306만 토큰 |

여기에 CLI 고정 오버헤드가 호출마다 얹힌다. **배치가 필수라는 §1 의 결론은 그대로다** —

## 11. 27번을 넣으면서 나온 것

### 11.1 "JSON 이면 봉투"로 가르면 본문이 통째로 빈다

## 12. 사내 프록시로 외부 설치가 된다 (2026-09-08)

사내 Windows PC 에서 HTTP 프록시를 거치면 패키지 설치가 된다. pip 로 확인했다.

    python -m pip install ... --proxy "http://<사내 프록시>:8080" --trusted-host pypi.org ...

**프록시 주소는 문서에 안 적는다.** 사내망 구성이라 저장소에 남기지 않는다.

### 12.1 무엇에 쓰는가

| 대상 | 명령 | 푸는 것 |
|---|---|---|
| 앱 운영 의존성 | `cd app; npm ci --omit=dev` | **17 · 18 자가검사 실행** |
| 스파이크 의존성 | `cd spikes; npm install` | 시험용 원본 생성 |

Codex 는 여기 없다. 19번과 W3b 는 보류다 (§9.3).

**`--omit=dev` 를 빼면 안 된다.** 그냥 `npm ci` 는 electron 을 같이 깐다. electron 은
설치 뒤에 100MB 짜리 바이너리를 GitHub 릴리스에서 받아 오는데, 그 자리는 패키지
레지스트리가 아니어서 사내 프록시로도 잘 막힌다. **자가검사는 electron 을 안 쓴다.** 실측으로 확인했다 —
운영 의존성만 깔면 162개 · 155MB 이고 자가검사 12건이 그대로 통과한다 (전체는 607MB).

`npm run smoke:win` 만 electron 이 필요하다. 그건 CI 가 `windows-latest` 에서 이미 돌리므로
사내 PC 에서는 안 해도 된다.

회수 스크립트 셋(`record.mjs` · `gemini-schema-check.mjs` · `token-ratio.mjs`)과 배포본
exe 는 그대로 설치가 필요 없다.

### 12.2 확인 안 된 것 셋

1. **npm 레지스트리가 같은 프록시로 통하는가.** 본 것은 pypi 뿐이다. `npm ping` 한 줄
2. **TLS 를 가로채는가.** 그러면 `SELF_SIGNED_CERT_IN_CHAIN` 이 난다. 회사 CA 를
   `npm config set cafile` 로 넣는 것이 정답이다. `strict-ssl false` 는 마지막 수단이다
3. **깔리는 것과 도는 것은 다르다.** 레지스트리가 열려도 실행 때 밖으로 나가는 길은
   따로 확인해야 한다

### 12.3 17 · 18 이 이걸 쓴다

자가검사 스크립트는 앱의 추출기와 유사도 코드를 그대로 부른다. 사내 PC 에 `app` 의존성이
깔려 있어야 돈다. 절차는 §13 에 있다.

## 13. 17 · 18 을 사내에서 돌리는 법

두 스크립트가 앱의 추출기와 유사도 코드를 그대로 부른다. **여기서 다시 구현하면 앱과

### 13.1 준비 — 순서가 중요하다

이름 목록을 한 줄에 하나씩 담은 텍스트 파일을 만든다. 위키의 엔티티 제목이어도 되고

**Lint 는 페이지 id 를 주는데 거부는 이름으로 저장한다.** 화면이 `ent-a` 를 보여주면
사람이 판정할 수 없다. 그렇다고 화면이 id 를 이름으로 되짚게 하면 페이지 목록을 또
읽어야 한다. `Finding` 에 `labels` 를 붙여 #9 이 제목을 같이 넘긴다.

실제 앱을 띄워 왕복을 봤다. 비슷한 엔티티 두 장을 넣고 [다른 대상이다] 를 누르니 후보가
0 이 되고 거부 목록에 1쌍이 남았으며 `.sb/dedup-rejected.json` 이 생겼다.

같이 고친 것 둘:

- 레일 버튼에 아이콘을 붙였다가 뺐다. [판단 검사] · [슬라이드] 에 없어서 혼자만 붙으면 어긋난다
- 마침표 뒤 공백이 JSX 에서 씹혀 "있습니다.**동기화가**" 로 붙어 나왔다

### 14.9 허브 묶음을 릴리스에 같이 올린다

Ubuntu 허브 PC 는 인터넷이 없다. `co-hub-<판>.tgz` 를 exe 와 같이 올려 받아서 옮기게
했다. **12 KB 다** — 런타임 의존성이 없어서 `dist/` 와 `deploy/` 만 담으면 끝난다.

`tsc` 만 돌아서 windows-latest 에서 만들어도 결과가 같다. 리눅스 러너를 따로 띄우지
않는다.

푼 것을 실제로 띄워 `/v1/health` 가 `{"ok":true}` 를 주는 것까지 봤다. 그러면서 문서
두 군데를 고쳤다. 시작할 때 `co-hub 0.0.0.0:8787 · /srv/co-hub` 를 찍는데 "아무 말도
안 한다" 고 적어 뒀다. Node 22 의 `ExperimentalWarning: SQLite` 도 안 적어 뒀다.

## 15. 첫 실사용에서 나온 화면 요청 (2026-09-09)

사내 PC 에서 `sample_playbook.md` 로 한 바퀴 돌린 사람이 여덟 가지를 짚었다. 여섯은
화면이고 하나는 계약이며 하나는 질문이다. 아래는 무엇을 왜 그렇게 고쳤는지다.

### 15.1 md 소스가 화면에 그대로 나왔다

원문 뷰어가 조각 본문을 `white-space: pre-wrap` 으로 그대로 찍었다. 변환기가 만든
md 에는 `</td>` · `<br>` 이 섞여 있어 그것이 그대로 보였다.

`core/md.ts` 를 새로 만들어 블록으로 자르고 `renderer/Markdown.tsx` 가 그린다.
**HTML 을 HTML 로 그리지 않는다** — `dangerouslySetInnerHTML` 을 안 쓴다. 위키는
LLM 이 만든 글을 담는 곳이라 거기서 태그가 살아나면 그게 곧 주입 통로다.

태그는 글자로 내린다. 그냥 지우면 표의 칸이 다 붙어 버려서 이렇게 바꾼다.

| 들어온 것 | 나가는 것 |
|---|---|
| `<br>` `<br/>` | 줄바꿈 |
| `</p>` `</tr>` `</div>` `</li>` `</h1>`…`</h6>` | 줄바꿈 |
| `</td>` `</th>` | ` · ` |
| 나머지 태그 | 지운다 |
| `&amp;` `&nbsp;` `&#65;` … | 푼다 |

라이브러리를 안 붙였다. 사내망에서 패키지 하나를 늘리는 비용이 여기 필요한 문법보다
크다 (`icons.tsx` 와 같은 이유). 지원 범위는 제목·문단·목록·인용·코드 펜스·구분선·
파이프 표와 인라인의 굵게·기울임·코드·링크·위키링크다. 앞머리 YAML 은 코드 블록으로
남긴다 — 감추면 무엇을 보고 있는지 알 수 없다.

**각주 인용(`[^src-a#p1]`)은 글자로 둔다.** 화면이 따로 칩으로 그리기 때문에 여기서
링크로 바꾸면 같은 것이 두 번 나온다.

[렌더링]·[원본] 토글은 **검색 결과와 원문 뷰어가 같은 값을 쓴다.** 따로 두면 어느 쪽이
켜졌는지 사람이 못 따라간다.

### 15.2 검색과 질의를 구별하지 못했다

검색창 하나에 두 가지가 걸려 있었다. 글자를 넣으면 원본 검색이 돈다. 버튼을 누르면
LLM 이 위키를 읽는다. 화면에는 "위키에 묻기" 한 줄뿐이었다.

- 결과 목록 위에 **원본 검색 결과 N건** 을 적었다
- 버튼을 **[LLM 위키에 묻기 (claude-code)]** 로 바꿨다. 괄호 안이 실제로 도는 CLI 다
- [이 원본으로 위키 갱신] 에도 같은 괄호를 붙였다

공급자 이름은 `taskProviders()` 로 미리 받는다. **누르기 전에 알려 준다** — 눌러 본
뒤에 "내장 MCP 서버에 붙을 수 있는 공급자여야 합니다" 를 보는 것은 늦다. 라우팅이
거절하는 상태면 버튼이 잠기고 사유가 옆에 뜬다.

### 15.3 도는 동안 아무것도 안 보였다

CLI 가 최대 5분까지 돈다 (`agent/exec.ts` `TIMEOUT_MS`). 그동안 화면에는 스켈레톤
막대 하나뿐이었고 끊을 방법이 없었다.

- `Exec` 계약에 `onOutput` 과 `signal` 을 넣었다. 어댑터 둘이 그대로 넘긴다
- `Store` 가 호출 하나를 `#runAgent` 로 감싼다. **동시에 하나만 돈다** — 두 개가
  돌면 취소가 어느 것을 끊는지 알 수 없고 지출도 예상의 두 배가 된다
- main → 렌더러로 미는 채널을 하나 뒀다 (`sb:agentOutput`). 표면에서 유일하게
  렌더러가 묻지 않고 받는 자리다
- 화면 아래에 진행 막대가 뜬다. 작업 이름 · 공급자 · 경과 초 · [취소] · 흐르는 글

**흐르는 글에 기대를 걸면 안 된다.** `claude --output-format json` 은 결과를 끝에 한
덩어리로 준다. 그래서 도는 동안 보이는 것은 주로 stderr 이고 비어 있을 수도 있다.
그래서 경과 초를 같이 센다. `--output-format stream-json` 이 매 조각을 주는 것은
`--help` 에서 확인했지만 `--json-schema` 와 같이 썼을 때 `structured_output` 이
그대로 오는지는 **안 재 봤다.** 재기 전에는 안 바꾼다.

취소는 실패와 다르게 적는다. `#cancelled` 를 보고 "취소했습니다" 를 돌려준다.

### 15.4 한 번 받은 변경안을 [버리기] 로만 나갈 수 있었다

CLI 를 한 번 부르면 돈이 나간다. 그런데 검토 화면을 벗어나는 길이 [버리기] 뿐이라,
잠깐 다른 것을 보려면 그 결과를 통째로 버려야 했다.

[전체 보류] 를 넣었다. 지금 고른 승인·보류 상태 그대로 `.sb/held-review.json` 에
두고 나간다. 레일에 **[검토 대기 N건]** 이 뜨고 눌러서 이어서 본다.

**이것이 변경안이 디스크에 닿는 유일한 자리다.** 설계 원칙 1번(LLM 은 디스크에 직접
쓰지 않는다)은 그대로다. 파일을 쓰는 것은 사람이 누른 [전체 보류] 다. 자리도 위키가
아닌 `.sb/` 이고 거기 있다는 것만으로는 아무것도 적용되지 않는다. 다시 열 때
**관문을 처음부터 다시 돌린다.** 보류하는 동안 Obsidian 으로 페이지를 고쳤을 수 있다.

적용하거나 버리면 그 파일도 같이 지운다. 적용했는데 다음에 또 뜨면 적용한 것이 아니다.

### 15.5 [버리기] 가 한 번에 지워졌다

휴지통 아이콘으로 바꾸고 확인 줄을 하나 뒀다. 확인 문구에 **다시 받으려면 CLI 를 또
불러야 한다**는 것과 [전체 보류] 가 있다는 것을 같이 적는다. 되돌릴 수 없는 것을
누르기 전에 대안을 보여 주는 편이 낫다.

### 15.6 보류·승인 체크박스가 안 읽혔다

체크박스는 "지금 어느 쪽인가" 만 보이고 "누르면 무엇이 되는가" 가 안 보인다. 두 칸을
다 그리는 토글로 바꿨다. 보류 쪽은 회색, 승인 쪽은 `--ok-wash` 다.

### 15.7 승인 3 · 보류 0 인데 적용 버튼이 안 열렸다 (버그 제보)

**판정은 맞았다.** 관문 5 에 걸린 페이지를 승인 목록에 넣으면 `applyBlockReason` 이
막는다. 잘못된 것은 그 사실을 화면이 못 전한 것이다. 셋 다 고쳤다.

1. 머리줄에 **문제 있는데 승인 N** 을 같이 센다. `승인 3 · 보류 0` 만 보면 왜 막혔는지
   단서가 없다
2. 막힌 사유가 버튼이다. 누르면 그 카드로 스크롤한다. 사유만 읽고 카드 스무 장에서
   눈으로 찾게 하면 안 된다
3. **[문제 있는 N건 빼기]** 를 넣었다. 한 번에 승인 목록에서 뺀다 (`dropFlagged`)

관문 위반 칸은 빨강(`--danger`)에서 `--warn-wash` 로 내렸다. **위반은 사람이 처리할
일이다.** 빨간 칸으로 보이면 앱이 고장 난 것으로 읽힌다 — 실제로 그렇게 읽혔다.
그리고 사유 아래에 무엇을 하면 풀리는지 한 줄을 붙였다.

| 관문 | 붙인 안내 |
|---|---|
| 4 | 출처 없는 주장. [편집] 으로 근거를 붙이거나 그 문장을 지운다 |
| 5 | 원본에 없는 자리를 인용했다. [편집] 으로 그 인용을 지우거나 맞는 앵커로 고친다. **원본을 안 고쳐도 된다** |
| 9 | 열람 등급이 원본보다 낮다. 앞머리의 `classification` 을 올린다 |

관문 5 는 LLM 이 없는 앵커를 지어낸 것이라 원본에는 아무 문제가 없다. 그 말을 안
적어 두면 사람이 원본을 의심한다.

### 15.8 Gemini 를 MCP 에 붙일 수 없나 (질문)

못 붙인다. 2026-09-05 실측이고 [`M2-PLAN.md`](M2-PLAN.md) §12.2 에 있다. Gemini CLI
에는 `--mcp-config` 가 없다. 격리 작업 디렉터리를 쓰면 그 폴더가 신뢰되지 않아 MCP 가
통째로 꺼진다. `--skip-trust` 는 대화형 확인만 건너뛴다.

지금 상태에서 남는 길은 셋이고 셋 다 대가가 있다.

| 길 | 대가 |
|---|---|
| 사내 PC 의 사용자 수준 Gemini 설정에서 폴더 신뢰를 끈다 | 앱이 사람의 기존 설정을 건드린다. `PLAN.md` §7.2 가 `--mcp-config` 를 고른 이유와 정면으로 충돌한다 |
| 질의도 밀어 넣기로 돌린다 | 위키 전체를 프롬프트에 넣는다. 커질수록 못 쓴다 |
| 하이브리드 검색으로 고른 후보 페이지만 밀어 넣는다 | **안 재 봤다.** 답변 품질이 MCP 경로와 같은지 모른다 |

셋째가 유망해 보이지만 **추측입니다.** 재기 전에는 안 넣는다. 그때까지 `query` 는
`claude-code` 로만 간다.

## 16. Gemini 를 읽기 경로에 넣었다 (2026-09-09)

사용자가 사내 PC 의 **전역** Gemini 설정(`~/.gemini/settings.json`)에
`security.folderTrust.enabled: false` 를 넣었다. §15.8 에서 "대가가 있다" 고 적은 첫째
길을 사용자가 고른 것이다. 그에 맞춰 앱을 고쳤다.

### 16.1 무엇을 재고 무엇을 안 쟀나

이 컨테이너에서 잰 것 (모델 호출 없음, 비용 0):

| 잰 것 | 결과 |
|---|---|
| `gemini mcp add -s project` 가 쓰는 자리 | `<cwd>/.gemini/settings.json` |
| 그 파일의 모양 | `{ "mcpServers": { "<이름>": { command, args, trust } } }` |
| 서버를 좁히는 플래그 | `--allowed-mcp-server-names <이름...>` |
| `--allowed-tools` | 있지만 **DEPRECATED** 라고 적혀 있다. 안 쓴다 |
| `--mcp-config` | **없다.** 설정 파일만 읽는다 |

**안 잰 것:** 그 설정을 끈 기계에서 Gemini 가 MCP 도구를 실제로 부르는가. 그 기계가
사내에만 있다. 이 컨테이너에는 Gemini 인증이 없어 봉투가 auth 오류(code=41)로 끝난다.

### 16.2 그래서 조용히 틀리지 않게 막았다

MCP 가 꺼져도 모델은 답을 낸다. 위키를 안 읽고 아는 대로 답한 것인데 **사람은 그것을
구별할 방법이 없다.** 그래서 어댑터가 stderr 을 보고 답을 버린다.

```
Warning: MCP servers are configured but disabled because this folder is untrusted.
```

문구는 2026-09-05 사내 실측에서 받은 그대로다 ([`M2-PLAN.md`](M2-PLAN.md) §12.2).
판이 올라 문구가 달라져도 걸리도록 `untrusted` 와 `mcp` 두 낱말로 본다.
`mcp` 를 안 쓰는 호출(밀어 넣기 경로)은 같은 경고를 봐도 그냥 간다.

### 16.3 목록을 둘로 나눴다

| 목록 | 정하는 것 | 지금 |
|---|---|---|
| `MCP_CAPABLE` | 라우팅이 보내도 되는가 | `claude-code` · **`gemini`** |
| `MCP_VERIFIED` | 되던 경로를 바꿔도 되는가 | `claude-code` |

`lint.judgment` 는 밀어 넣기로 이미 돌고 있고 두 방식이 같은 문제를 잡는다
([`M2-PLAN.md`](M2-PLAN.md) §13.1). 확인 전에 그 경로를 당겨 가기로 갈아 끼우면
**되던 것이 깨질 수 있다.** 아껴지는 토큰보다 손해가 크다. 사내에서 확인되면
`MCP_VERIFIED` 를 지우고 목록 하나로 되돌린다.

### 16.4 사내에서 확인하는 법

```powershell
cd spikes\cli
node gemini-mcp-check.mjs
```

임시 폴더에 표식 하나를 두고 모델이 그것을 도구로 가져오는지 본다. **문서를 안 읽고 안
내보낸다.** 화면에 나오는 것은 세 줄이다.

```
1 신뢰 게이트가 MCP 를 껐는가 : 안 껐음 / 껐음
2 도구를 실제로 불렀는가     : 불렀음 / 못 불렀음
3 종료 코드                  : 0
```

둘 다 통과하면 알려 주십시오. `MCP_VERIFIED` 를 지우고 `lint.judgment` 도 당겨 가기로
돌립니다. 1번이 "껐음" 이면 전역 설정이 안 먹은 것입니다. 그 상태에서도 앱은 답을
버리므로 질의가 막힐 뿐 틀린 답이 나오지는 않습니다.

`--selftest` 는 CLI 를 안 부르고 스크립트 자신만 본다 (9건).

### 16.5 1회차는 표본이 아니었다 — 종료 코드 41

사내 1회차 결과는 `안 껐음 / 못 불렀음 / 41` 이었다. **이것은 "Gemini 가 MCP 에 못
붙는다" 가 아니다.** 41 은 Gemini 의 오류 봉투이고 stderr 로 온다 (0.58.0 실측,
§11.1 · `agent/gemini.ts` `parseEnvelope`). 인증이나 쿼터에서 나는 코드다. CLI 가
답을 못 낸 회차라 2번 줄은 판정이 아니다.

스크립트가 그 구별을 안 해 준 것이 문제였다. 세 줄을 찍고 나서야 stderr 를 400자
잘라 냈다. 그 줄이 판정처럼 읽혔다. 두 가지를 고쳤다.

- 종료 코드가 0 이 아니면 **판정을 비우고 2 로 나간다.** PASS/FAIL 을 안 찍는다
- 오류 봉투에서 `message` 와 `code` 를 꺼내 한 줄로 낸다 (`errorOf`). 도구가 낸
  메시지라 사내 문서가 아니다

다음 회차에서 볼 것은 **사유 한 줄**이다. 인증이면 사내 기업계정 로그인을 다시
한다. 쿼터면 날이 바뀐 뒤에 돌린다. 그 뒤에야 1·2번 줄이 표본이 된다.

## 17. 두 번째 실사용에서 나온 화면 요청 (2026-09-09)

v0.9.1 을 쓰면서 나온 아홉 가지다. 여덟은 화면이고 하나는 표시가 거짓말을 하던 것이다.

### 17.1 Vault 종류를 두 벌로 판정하고 있었다

개인 Vault 를 만들었는데 설정에 `CO 영역` 으로 나왔다. 같은 것을 두 자리가 다른
규칙으로 보고 있었다.

| 자리 | 규칙 | 결과 |
|---|---|---|
| 좌측 레일 배지 | `config.hub !== null` | 개인 |
| 설정 화면 "종류" | `config.id === 'personal'` | CO 영역 |

`main.ts` 의 `pickVault` 는 새 Vault 를 `{ id: 폴더이름 }` 으로 만든다. id 가
`personal` 인 Vault 는 **화면에서 만들 수가 없다.** 그래서 설정 화면은 개인 Vault 를
한 번도 개인이라고 말한 적이 없었다.

시험이 이걸 못 잡은 이유도 같다. `store.test.ts` 가 `{ id: 'personal' }` 로 열고
있었는데, 그것은 화면이 만드는 모양이 아니다. **시험이 제품 경로를 안 밟고 있었다.**

허브 부착 여부(`config.hub`)로 통일했다. 레일과 같은 규칙이다. `AppSettings.personal`
은 `co` 로 이름을 바꿨다 — 같은 이름으로 다른 것을 뜻하던 `HubStatus.personal`
(`id === 'personal'`, 허브에 붙는 것 자체를 막는 규칙) 과 헷갈리지 않게 했다.

시험도 폴더 이름으로 만든 Vault 를 열어 확인하도록 고쳤다.

### 17.2 공급자를 바꿔도 버튼은 옛 이름을 달고 있었다

설정에서 CLI 를 바꾸면 라디오만 갱신됐다. 버튼에 적힌 `(claude-code)` 는 다음
`refresh()` 까지 그대로였다. 무언가 한 번 실행해야 바뀌는 것처럼 보였다.
`pickProvider` 가 `taskProviders()` 도 같이 다시 읽는다.

### 17.3 원본이 위키에 들어갔는지 표시한다

좌측 목록의 각 줄에 표시를 붙였다. 판정 기준이 중요하다.

**`manifest` 의 `proposedAt` 을 안 쓴다.** 그것은 "변경안을 만들었다" 이지 "사람이
승인해서 위키에 들어갔다" 가 아니다. 제안만 하고 버린 원본을 반영됨으로 그리면
표시가 거짓말이 된다. 대신 **위키가 그 원본을 인용하고 있는가** 를 본다
(`store.citedSources`) — 본문의 앵커 인용과 front-matter 의 `claims.source` 둘 다
센다. 페이지를 지우면 표시도 저절로 빠진다.

위키 전체를 읽는 일이라 `listSources` 안에 넣지 않고 창구를 따로 냈다. 원본 목록만
필요한 자리(`plan` · 앵커 수집)까지 이 비용을 물면 안 된다.

### 17.4 나머지 여섯

- 원본 목록에 [새로 고침] 을 넣었다. 폴더를 앱 밖에서 고쳤을 때 창을 껐다 켜지
  않아도 된다. 원본과 받은 편지함을 다시 읽는다
- 뷰어 버튼을 `이 원본으로 위키 갱신` 에서 `위키 갱신` 으로 줄였다. 글자 크기도
  옆의 [렌더링] 토글에 맞췄다. 머리글 줄에서 하나만 커 보이면 안 된다
- [슬라이드] 를 [내보내기] 로 고쳤다
- [판단 검사] · [내보내기] · [중복 후보] 를 한 줄에 같은 폭으로 뒀다. 글자 크기는
  아래 [설정] 줄에 맞췄다
- 좌측 하단에서 `남은 문서 약 N건` 을 뺐다. 이번 달 쓴 돈만 적는다.
  **되돌린 판단이다** ([`M2-PLAN.md`](M2-PLAN.md) §3.4 는 달러보다 건수를 앞에 두라고
  했다). 뺀 이유는 그 건수가 문서당 단가 표본 몇 건에서 나온 추정이라, 건수로 바꾸면
  실제보다 정확해 보이기 때문이다. `documentsLeft` 는 계속 계산해 둔다
- 진행 막대와 인제스트 결과 팝업이 겹쳤다. 진행 막대는 가운데, 결과는 오른쪽이라
  창이 좁으면 만났다. 화면 아래 한 칸에 세로로 쌓아 어느 폭에서도 안 겹치게 했다.
  결과 팝업이 오른쪽에서 가운데로 옮겨 온 것이 이 변경의 대가다

## 18. 사내 1회차 인증 오류 — 우리 코드가 아니다 (2026-09-09)

2회차 결과가 명확했다.

```
Please set an Auth method in your C:\Users\...\.gemini\settings.json or specify one of
the following environment variables: GEMINI_API_KEY, GOOGLE_GENAI_USE_VERTEXAI, GOOGLE_GENAI_USE_GCA
```

같이 온 보고가 더 중요하다 — **v0.9.0 에서는 위키 갱신이 됐는데 v0.9.1 에서는 안 된다.**
판이 원인처럼 보이는 상황이라 코드부터 봤다.

### 18.1 v0.9.1 은 위키 갱신 경로의 인자를 안 건드렸다

`gemini.ts` 의 `buildArgv(job.mcp !== undefined)` 가 새로 생겼다. 그런데 위키 갱신은
`store.propose()` 이고 거기서는 `job.mcp` 를 안 넘긴다. 밀어 넣기 경로라 MCP 가 필요
없기 때문이다. 그래서 `buildArgv(false)` 가 되고 **인자가 v0.9.0 과 글자까지 같다.**
바뀐 것은 `onOutput` 과 `signal` 뿐이고 둘 다 인자에 안 들어간다.

### 18.2 원인은 전역 설정 편집이다

0.58.0 의 `validateNonInteractiveAuth` 를 읽었다. 인증을
`settings.merged.security.auth.selectedType` 에서 찾고, 없으면 저 문구를 낸다.
`security.folderTrust.enabled` 와 **같은 `security` 아래**다.

시간 순서가 맞는다. v0.9.0 은 됐고 → 전역 설정에 `folderTrust` 를 넣었고 → 그 뒤로
v0.9.1 과 스파이크가 둘 다 인증에서 막혔다. `security` 를 통째로 새로 쓰면 형제인
`auth` 가 같이 지워진다. **판이 아니라 편집이 걸린 것이다.**

고치는 법은 둘 중 하나다.

```jsonc
{
  "security": {
    "auth": { "selectedType": "..." },        // 지워진 것
    "folderTrust": { "enabled": false }       // 넣은 것
  }
}
```

`selectedType` 값을 손으로 짐작하지 말고 터미널에서 `gemini` 를 한 번 띄워 인증
방식을 고르면 CLI 가 알아서 적는다. 값은 `oauth-personal` · `gemini-api-key` ·
`vertex-ai` · `cloud-shell` 중 하나다 (0.58.0 번들에서 확인).

### 18.3 앱이 무엇을 하게 했나

인증은 CLI 가 자기 설정에 들고 있고 앱은 거기 손대지 않는다. 그러니 앱이 할 수 있는
것은 **무엇을 해야 하는지 알려 주는 것**뿐이다. `authHint()` 를 넣어 그 오류일 때만
한 줄을 붙인다. 다른 오류에는 안 붙인다 — 늘 붙는 안내는 곧 안 읽힌다.

**아직 안 고쳤다.** 검색 결과 순서가 바뀌는 변경이라 릴리스와 같이 넣지 않았다.

## 20. 사내 W-O 1회차 — 통과했고 수치 하나는 표본이 아니다 (2026-09-10)

사내 PC 에서 [`spikes/local/ollama-check.mjs`](../spikes/local/ollama-check.mjs) 를
돌렸다. 회수한 것은 이것뿐이다.

| 항목 | 값 |
|---|---|
| W-O1 두 모델 | 있다 |
| W-O2 차원 | 1,024 |
| W-O2 속도 | 청크당 1,842ms |
| W-O3 스키마 일치 | 5/5 |
| W-O4 지어낸 앵커 | 0건 |
| 대화 회차당 | 20,793ms |

W-O3 과 W-O4 가 이 계획의 관문이었다. 둘 다 통과했다. 특히 W-O4 가 0건인 것은

### 20.1 청크당 1,842ms 는 처리량이 아니다

**이 수치는 그대로 쓰면 안 된다.** 스크립트가 `/api/embed` 를 한 번만 부르고 그 시간을
청크 셋으로 나눴는데, 그 첫 회차에는 BGE-M3 를 메모리에 올리는 시간이 통째로 들어 있다.
적재는 한 번뿐이고 처리량은 청크 수만큼 곱해지므로 둘을 같은 값으로 보면 색인 시간을
크게 틀리게 잡는다.

`LOCAL-LLM.md` §7 에 "청크당 1초면 83분이라 다른 설계가 필요하다" 고 적어 놓았다.
그 판정을 이 수치로 내리지 않는다. 표본이 아니기 때문이다 (`CLAUDE.md` §5).

그래서 스크립트를 고쳤다. 예열 호출을 한 번 하고 버린 뒤, 서로 다른 합성 청크 열두
개를 한 번에 넣어 처리량을 잰다. 화면에 두 줄이 따로 나온다.

```
      적재 포함 첫 호출 5528ms (한 번만 든다)
      예열 뒤 청크당 91ms — 5,000 청크면 약 8분
```

두 번째 줄이 색인 시간을 정하는 값이다. **아직 안 쟀다.**

### 20.2 그래도 설계를 느린 쪽에 맞췄다

예열 뒤 수치가 어떻게 나오든 안전한 쪽으로 만들었다.

- 임베딩은 **본문이 그대로면 다시 안 만든다.** 청크 본문의 해시를 벡터와 같이 적어 두고
  다음 회차에 그대로인 것을 건너뛴다 (`core/local/file.ts`)
- 중간에 끊어도 그때까지 만든 것을 저장한다. 다음에 이어서 만든다
- **임베딩이 없어도 답이 나온다.** 그때는 키워드(BM25)로만 찾는다. 색인이 없다고
  질의가 막히면 처음 쓰는 사람이 두 시간을 기다려야 한다

### 20.3 대화 회차당 20.8초

로컬 답변 한 번에 20초 남짓 걸린다는 뜻이다. 클라우드 CLI 보다 느리다. 다만 이 경로는
**돈이 안 들고 내용이 이 컴퓨터를 안 떠난다.** 그 대가로 받아들일 값이라고 본다.
`n=5` 이고 조각 셋짜리 짧은 프롬프트에서 잰 값이라, 실제 위키 조각 여덟 개를 넣으면
더 걸린다. 그 수치는 아직 없다.

## 21. 로컬 질의 경로를 만들었다 (2026-09-10)

[`LOCAL-LLM.md`](LOCAL-LLM.md) 의 §2.2 구조를 그대로 구현했다. 검토 문서와 달라진 곳만
적는다.

### 21.1 검색 순위 결함을 먼저 고쳤다 (19번의 숙제)

`core/search.ts` 가 rowid 를 `Set` 대신 **순서 있는 배열**에 모은다. 본문을 다시 읽은
뒤 그 순서대로 되돌린다. 접두 색인 결과가 먼저 오고 그 뒤에 trigram 결과가
온다. 각 목록 안에서는 FTS5 가 매긴 BM25 순위 그대로다.

회귀 검사는 결함의 모양을 그대로 쓴다. 예전에는 `IN` 이 rowid 오름차순으로 돌려줘서
**먼저 넣은 것이 먼저 나왔다.** 그래서 제일 잘 맞는 짧은 청크를 맨 나중에 넣고 그것이
첫 줄에 오는지 본다.

### 21.2 위키 색인은 파일로 안 남긴다

질의마다 메모리에 새로 만든다 (`:memory:` SQLite). 승인 한 번에 위키가 바뀌므로 파일로
남기면 언제 무효인지를 따로 관리해야 한다. 5,000 청크를 FTS5 에 넣는 값이 그 관리
비용보다 싸다. 임베딩은 만드는 데 시간이 크게 드니 반대로 파일에 남긴다.

### 21.3 낱말 단위로 묻는다

FTS5 에 질문 문장을 통째로 넣으면 구 매칭이라 거의 안 걸린다. 그래서 낱말로 가른다.
색인이 접두 매칭이라 조사가 붙어도 어절 앞부분은 잡히지만, "갱신일은" 으로 물으면
"갱신일이" 를 못 잡는다. 그래서 아는 조사를 뗀 것도 같이 넣는다.

**뗀 것이 틀려도 손해가 없다.** 결과를 RRF 로 합치므로 헛짚은 낱말은 빈 목록을 보태고
끝난다. 임계값으로 거르는 구조였다면 이렇게 못 한다 (`CLAUDE.md` §7).

낱말마다 목록이 하나씩 나오므로 **그것끼리 먼저 합치고** 그다음 임베딩 목록과 합친다.
한 번에 합치면 낱말 수만큼 키워드 쪽이 무거워진다.

### 21.4 관문 5 가 여기서는 좁아진다

MCP 로 당겨 가는 경로에서는 모델이 무엇을 읽었는지 앱이 모른다. 그래서 앵커 실재 검사가
Vault 전체를 놓고 판정한다. 로컬 경로는 앱이 조각을 골라서 넣으므로 **준 조각에 없는
앵커는 지어낸 것이 확실하다.** 하나라도 걸리면 답을 통째로 거부한다.

### 21.5 지출 계량기에 0 을 안 더한다

`LOCAL-LLM.md` §5 에는 0 을 더한다고 적었다. 안 했다. 계량기는 공급자 id 로 줄을
가르는데 로컬 모델에는 그 id 가 없다. 넷째 id 를 만드는 것은 §5 가 하지 말라고 한 바로
그것이다. 화면에는 `costUsd: 0` 이 그대로 뜬다.

### 21.6 화면

- 설정에 [위키에 묻기] 축이 생겼다. LLM CLI 설정과 **다른 축**이다 — 위키 갱신은 이 값과
  무관하게 늘 CLI 가 맡는다
- 로컬을 고르면 주소와 모델 이름 세 칸, [임베딩 만들기] 버튼, 상태 한 줄이 나온다
- 버튼 이름이 `위키에 묻기` 로 짧아졌고 괄호 안이 `(로컬)` 이 된다

## 22. 사라진 원본을 어떻게 다룰까 (2026-09-10)

사람이 탐색기에서 `01_SOURCES/` 의 파일을 지웠을 때 앱이 무엇을 해야 하는지 정했다.

### 22.1 두 사건을 갈랐다

원문 파일이 없어진 것과 "그런 주장은 없었다" 는 다른 사건이다. 추출물
(`.sb/extracted/*.json`)은 **앵커 실재 검사(관문 5)의 근거**다. 파일의 사본으로 두면 안 된다.
그것을 지우면 그 원본을 인용한 위키 페이지가 전부 검사에서 막힌다.

그래서 이렇게 가른다.

| 상태 | 하는 일 |
|---|---|
| 위키가 안 쓰는 원본 | 추출물 · 색인 · manifest 에서 뺀다 |
| 위키가 인용 중인 원본 | 근거를 남기고 목록에서 취소선으로만 표시한다 |

**원본 파일을 앱이 지우지 않는다.** 사람이 지운 것을 따라갈 뿐이다.

### 22.2 언제 도나

[새로 고침] 이 부른다. 목록을 다시 읽기만 하던 버튼이 정리까지 맡는다. 무엇을 뺐고
무엇을 남겼는지 한 줄로 알려 준다.

표시(`missing`)는 정리와 따로 계산한다. `01_SOURCES/` 를 한 번 읽어 이름으로 맞추므로
파일을 지운 직후 목록을 다시 읽기만 해도 흐려진다.

## 23. Gemini CLI 인증을 사내 PC 에서 되살리는 법 (2026-09-10)

18번에서 진단한 것을 실제로 치는 명령으로 적는다. 전부 **파워쉘**이다.

```powershell
# 1. 지금 설정이 어떤지 본다. security.auth 가 없으면 그것이 원인이다
Get-Content "$env:USERPROFILE\.gemini\settings.json"

# 2. 손대기 전에 복사해 둔다
Copy-Item "$env:USERPROFILE\.gemini\settings.json" "$env:USERPROFILE\.gemini\settings.json.bak"

# 3. gemini 를 띄운다
gemini
```

띄운 화면에서 `/auth` 를 친다. 인증 방식 고르는 창이 뜬다. 사내 기업 계정이면
"Login with Google" 을 고르고 브라우저에서 계정을 고른다. 끝나면 `/quit` 으로 나온다.

```powershell
# 4. selectedType 이 적혔는지 확인한다
Get-Content "$env:USERPROFILE\.gemini\settings.json"

# 5. 실제로 답하는지 본다. 여기서 답이 나오면 앱에서도 된다
gemini -p "안녕"
```

### 23.1 손으로 값을 적지 않는 이유

`selectedType` 에 들어갈 수 있는 값은 넷이다 — `oauth-personal` · `gemini-api-key` ·
`vertex-ai` · `cloud-shell` (0.58.0 번들에서 확인). 어느 것인지는 사내 계정이 어떤
방식으로 붙는지에 달렸다. 여기서 짐작하면 틀린 값을 적어 놓고 다시 헤매게 된다.
`/auth` 로 고르면 CLI 가 알아서 적는다.

### 23.2 folderTrust 는 안 지워진다

`/auth` 가 부르는 저장 함수는 설정 객체에 **경로 하나만 덮어쓴다**
(`setNestedProperty` 뒤 저장, 0.58.0 번들에서 확인). 그래서 같은 `security` 아래
`folderTrust.enabled: false` 는 그대로 남는다. 3번을 하고 나서 4번으로 눈으로 한 번 더
확인하면 된다.

### 23.3 그래도 안 되면

`/auth signout` 을 치면 캐시한 자격 증명을 지우고 `selectedType` 도 지운다. 그다음
`/auth` 로 다시 고른다. 이것으로도 안 되면 그때는 사내 프록시나 계정 권한 쪽을 본다.

### 23.4 다음 회차

인증이 살아난 뒤에 `node spikes\cli\gemini-mcp-check.mjs` 를 다시 돌린다. **그때 나오는
세 줄이 처음으로 표본이다.** 종료 코드 41 로 끝난 회차는 판정이 아니다 (16.5 · 18).

## 24. 사내 2회차 — 두 수치와 결함 셋 (2026-09-10)

### 24.1 임베딩 처리량: 예열 뒤 청크당 26ms

20.1 에서 갈라 놓은 두 값 중 아래쪽이다. 5,000 청크면 **약 2분**이다. 처음 한 번 돌리고
그다음부터는 바뀐 페이지만 다시 만든다. `LOCAL-LLM.md` §7 이 걱정한 "청크당 1초면
83분" 은 일어나지 않는다.

1회차의 1,842ms 는 역시 모델 적재 시간이었다. 71배 차이다. 그 값으로 설계를 뒤집지
않은 것이 맞았다.

### 24.2 Gemini 는 MCP 에 붙어 놓고 도구를 안 부른다

W3c 재측정 결과다.

```
PASS  폴더 신뢰가 MCP 를 끄지 않는다
FAIL  모델이 내장 서버의 도구를 불렀다
```

`security.folderTrust.enabled: false` 는 제 일을 했다. 서버는 붙는다. 그런데 모델이
도구를 안 부른다.

**이것이 MCP 가 꺼진 것보다 나쁘다.** 꺼진 것은 stderr 에 자국이 남아 어댑터가
`mcpDisabled` 로 알아채고 답을 버린다. 붙어 놓고 안 쓴 것은 자국이 없다. 그대로 두면
위키를 안 읽고 아는 대로 답한 것이 인용까지 달고 화면에 뜬다.

그래서 `MCP_CAPABLE` 에서 Gemini 를 뺐다. 읽기 경로(`query` · `synthesis`)는 다시
Claude Code 만 간다. 상한에 걸려도 대신 안 보낸다. 기대에 맞게 규칙을 고치지 않는다
([`CLAUDE.md`](../CLAUDE.md) §9).

Gemini 는 밀어 넣기 경로(`lint.judgment` · `ingest.batch`)에 그대로 있다. 그쪽은 앱이
내용을 넣어 주므로 도구를 안 불러도 된다.

### 24.3 관문 5 가 너무 많이 걸려 사람이 손으로 지우고 있었다

`위키 갱신 (gemini)` 이 낸 변경안에서 "없는 앵커를 인용했습니다" 가 대량으로 났다.
승인하려면 사람이 본문에서 `[^src-...#...]` 를 하나씩 찾아 지워야 했다. **사용성 결함이
맞다.** 관문이 옳게 걸렸더라도 고치는 일을 사람에게 떠넘긴 것은 우리 쪽 문제다.

두 가지를 했다.

**표기 정규화.** 모델이 본문 표기를 그대로 베껴 `[^src-x#s-1]` 이나 `^src-x#s-1` 을
`claims[].source` 에 적는다. 읽는 자리(`parsePage`)에서 한 번 벗긴다. 내용이 맞는데
껍데기만 다른 것을 형식 오류로 막으면 안 된다. **실재 판정은 그대로 관문 5 가 한다.**

**[없는 앵커 N건 지우기] 버튼.** 검토 화면 머리에 뜬다. 본문 인용은 그 표기만 지우고
문장은 남긴다. front-matter 의 주장은 통째로 뺀다 — 출처 없는 주장은 관문 4 에서
어차피 막히고, 근거를 잃은 문장을 위키에 남기면 안 된다. 지운 결과는 **관문 일곱 개를
처음부터 다시 통과해야 한다.** 관문을 느슨하게 한 것이 아니다.

**아직 모르는 것:** 걸린 앵커가 형식만 틀린 것인지 아예 지어낸 것인지 구별하지 못했다.
프롬프트는 쓸 수 있는 앵커를 이미 목록으로 준다(`agent/ingest.ts`). 목록 밖의 것을
적었다면 프롬프트 문제이고, 목록 안의 것을 다르게 적었다면 표기 문제다. 거부된 앵커
한 줄과 그 원본의 실제 앵커 한 줄을 같이 회수해야 갈린다.

### 24.4 로컬 질의가 `^src-...` 로 막혔다

```
claims[0].source 가 앵커 형식이 아닙니다: ^src-20260903-esg로드쇼-투자자질의-분석 ...
```

24.3 과 같은 원인이다. Qwen2.5 도 본문 표기를 그대로 베꼈다. `parseAnswer` 가 껍데기를
벗기고 본다. 벗긴 뒤에도 형식이 아니면 그대로 막는다.

여기서 한 가지가 확인됐다. **로컬 경로에서 검색은 제 일을 했다** — 모델이 인용한
`src-20260903-esg로드쇼-투자자질의-분석` 은 질문("수자원 질문한 기관")과 맞는 원본이다.
막힌 곳은 형식 검사뿐이었다.
