## 0. 두 프로젝트의 관계

| | graphify | co-secondbrain |
|---|---|---|
| 대상 | 주로 **코드베이스** (+ 문서·PDF·이미지·영상) | **업무 문서** (이메일·전사·Office·PDF) |
| 산출물 | **지식 그래프** (`graph.json`, `graph.html`, `GRAPH_REPORT.md`) | **위키** (사람이 읽는 마크다운 산문 페이지) |
| 산출물의 성격 | **파생물.** 언제든 원본에서 재생성. 버려도 됨 | **자산.** 사람 승인을 거쳐 축적. 버리면 안 됨 |
| 형태 | Python 라이브러리 + 에이전트 스킬 | Electron 데스크톱 앱 |
| 사람 개입 | 없음 (자동 생성) | 필수 (diff 승인) |

**경쟁이 아니라 상보 관계입니다.** graphify는 원본에서 *구조*를 뽑고, 우리는 *산문*을 씁니다.
graphify의 그래프는 재생성 가능한 파생물이고, 우리 위키는 사람 손이 들어간 자산입니다.

따라서 "graphify를 쓰자"가 아니라 **"graphify가 푼 문제 중 우리도 겪을 것을 가져오자"** 입니다.

## 1. 지금 반영할 것 (권장)

### A. 신뢰도 태그를 3분류로 — 우리 설계의 명백한 개선

우리 front-matter의 `confidence: high | medium | low`는 **의미가 모호합니다.**
"high"가 무슨 뜻인지 사람마다 다르게 읽습니다.

graphify는 관계마다 **인식론적으로 명확한** 3분류를 붙입니다:

| 태그 | 의미 |
|---|---|
| `EXTRACTED` | 원본에 **명시**돼 있음 (문장 그대로 존재) |
| `INFERRED` | 모델의 합리적 추론. `confidence_score` 동반 |
| `AMBIGUOUS` | 불확실. **사람 검토 대상으로 리포트에 표시** |

INFERRED의 점수는 **자유 실수가 아니라 이산 루브릭**입니다. 이게 핵심입니다:

```
0.95  거의 확실 — 명시적 교차 참조, 타당한 대상이 하나뿐
0.85  강한 근거 — 명명과 맥락이 일치
0.75  타당함   — 맥락상 그럴듯하나 명시적이지 않음
0.65  약함     — 이름 유사성뿐
0.55  추측
```

모델에게 "0~1 사이 신뢰도를 매겨라"라고 하면 뭉개진 값이 나옵니다.
**다섯 개 중에 고르라고 하면 일관됩니다.**

**우리 적용:** 페이지 단위 `confidence`를 버리고 **주장(문장) 단위**로 태그를 답니다.
업무 위키에서 "계약 갱신일은 2027-01이다"가 계약서에 적혀 있는지(EXTRACTED)
메일 정황으로 추론한 것인지(INFERRED 0.75)는 결정적으로 다릅니다.
`AMBIGUOUS`는 Lint 결과함으로 자동 라우팅합니다.

### B. 결정론적 구조 추출을 지금보다 훨씬 깊게

graphify의 성능·비용 우위는 대부분 여기서 나옵니다. 코드는 tree-sitter AST로
**LLM 없이 전부** 뽑고("Graph build LLM credits: **0**"), LLM은 문서·이미지 의미 추출에만 씁니다.

우리 계획은 "텍스트 추출"까지만 하고 **구조는 전부 LLM에 맡기고 있었습니다.**
문서에도 공짜로 뽑을 수 있는 구조가 많습니다:

| 형식 | LLM 없이 뽑을 수 있는 것 (전부 `EXTRACTED`) |
|---|---|
| **이메일** | **`In-Reply-To` / `References` 헤더로 스레드 트리 복원.** 발신자↔수신자 그래프, 날짜 순서 |
| `.docx` | 제목 트리(H1>H2>H3), 각주, 상호참조 필드, 변경 이력·주석 |
| `.xlsx` | 시트→표→열 구조, 수식의 셀 참조 = **의존 그래프**, 명명 범위 |
| `.pptx` | 슬라이드 순서, 제목 계층, 발표자 노트, 도형 그룹 |
| `.pdf` | 목차(북마크), 내부 링크, 각주 |
| 전사 | 화자 턴, 타임코드, 발언 인접 관계 |
| 마크다운 | `[[wikilink]]`, `[text](./other.md)` → `references` 엣지 (graphify도 동일 처리) |

**이메일 스레드 복원을 완전히 놓치고 있었습니다.** 이메일은 우리 입력 형식 중 하나이고,
스레드는 그 자체로 지식 구조입니다. RFC 5322 헤더로 공짜로 복원됩니다.

`.xlsx` 수식의 셀 참조를 의존 그래프로 뽑는 것도 마찬가지입니다.
"이 숫자가 어디서 왔나"는 업무에서 가장 자주 나오는 질문입니다.

### C. 시맨틱 캐시 + manifest — 재실행 비용 제거

graphify는 파일마다 **SHA256 콘텐츠 해시**로 LLM 추출 결과를 캐싱합니다.
재실행 시 변경분만 LLM에 보냅니다. **파일 이름이 바뀌면 캐시된 결과의 `source_file`만
갱신**하고 재추출하지 않습니다.

훔칠 만한 디테일 하나: **`manifest.json`은 성공적으로 완료됐을 때만 쓴다.**
실행 중 크래시가 나도 다음 실행의 diff가 오염되지 않습니다.

우리 계획엔 파일 해시가 있지만 **LLM 결과 캐시는 없습니다.** 같은 원본을 다시 인제스트하면
CLI를 다시 돌립니다. 추가합니다.

### D. 엔티티 중복 제거 — 우리 계획의 가장 큰 구멍

**이게 없으면 6개월 뒤 위키가 망가집니다.**

우리 위키는 시간이 지나면 `에이콤(주)` / `Acme` / `ACME Corp` / `에이콤`을
**서로 다른 엔티티 페이지 4개**로 갖게 됩니다. front-matter에 `aliases:` 필드는
만들어 뒀지만 **그걸 채우는 절차가 계획에 없었습니다.**

graphify의 dedup 파이프라인 (임베딩·PyTorch 없이):

```
1. 정확 정규화        대소문자·구두점 변형
2. ★엔트로피 게이트    글자당 2.5비트 미만 라벨은 퍼지 매칭에서 제외
                      ("AI", "DB", "x" 같은 짧고 모호한 이름은 자동 병합이 위험)
3. MinHash + LSH      3-gram shingle, 128 permutation, threshold 0.7
                      → 후보쌍을 O(n²) 아닌 O(n)으로. 1만 노드에서 1초 미만
4. Jaro-Winkler       후보쌍을 0.92 이상에서 검증. 오타·복수형·띄어쓰기
5. 커뮤니티 보정      같은 클러스터에 속하면 +0.05
6. Union-find 병합    연결 요소를 하나로. 엣지 재배선, 자기루프 제거
7. LLM 타이브레이커   0.75~0.85 애매 구간만. 30개씩 배치. 기본 꺼짐
```

**2단계 엔트로피 게이트가 이 설계를 안전하게 만드는 부분입니다.**
짧은 이름을 자동 병합하면 서로 다른 개념이 합쳐지고, 위키에서 그건 복구가 어렵습니다.
LLM은 **애매한 구간에만** 부르는 것도 좋습니다 — 비용이 아니라 신뢰의 문제입니다.

**우리 적용:** Lint 검사 #9로 추가하고, 병합은 **자동이 아니라 diff 승인**을 거칩니다.
자동 병합은 우리 원칙(LLM은 디스크에 직접 쓰지 않는다)에 어긋납니다.

⚠️ **미검증:** MinHash의 3-gram shingle은 라틴 문자 기준 설계입니다.
graphify도 중국어는 별도 분절기(jieba)를 씁니다. **한국어 엔티티명에서의 정확도는
M0에서 실측해야 합니다.** 조사 결합("에이콤이", "에이콤은")과 띄어쓰기 변형이 관건입니다.

### E. 보안을 단일 관문으로

graphify는 모든 외부 입력이 `security.py` 한 곳을 통과합니다:
`validate_url`(http/https만, file:// 리다이렉트 차단), `safe_fetch`(크기 상한·타임아웃),
`validate_graph_path`(출력 디렉터리 안으로 resolve되는지), `sanitize_label`(제어문자 제거,
256자 상한, HTML 이스케이프).

우리 계획은 보안이 여기저기 흩어져 있습니다. 특히 **놓친 것 하나:**

> **LLM이 쓴 페이지 제목이 곧 파일 이름이 됩니다.**
> 모델이 `../../../Windows/System32/...` 같은 제목을 내면 경로 탈출입니다.

`sanitize_label` 동등물이 반드시 필요합니다. 슬러그 생성 시 제어문자·경로 구분자·
예약어(`CON`, `PRN`, `NUL` — Windows) 처리까지.

### F. `.sbignore` — 무시 규칙

graphify: `.graphifyignore`가 `.gitignore`와 **병합**되고, 하위 디렉터리 스코프가
git과 동일하게 동작하며, **"추가로 제외만 할 뿐 다시 포함시키지는 않는다"**.

우리는 무시 메커니즘이 아예 없습니다. `sources/`를 네트워크 공유에 걸면 필요해집니다.

### G. 비용 상한 레버

`GRAPHIFY_MAX_RETRY_DEPTH` — 잘린 청크를 재귀 이분해 재추출하는 깊이 상한(기본 3, 즉 한 청크가
최대 8배까지 호출될 수 있음). `0`이면 재시도 없이 청크당 정확히 1회.

우리에겐 **최악 비용 상한 개념이 없습니다.** 대용량 문서 하나가 조용히 비용을 폭증시킬 수
있습니다. 인제스트 작업마다 "최대 N회 호출" 상한을 둡니다.

### H. 쿼리 로그는 기본 꺼짐

graphify는 로컬 쿼리 로그를 **기본 비활성**으로 두고 3개 환경변수로 제어합니다
(`_ENABLE` / 경로 지정 / `_DISABLE`이 최우선). 회사 도구로서 옳은 자세라 그대로 가져옵니다.

## 2. 계획의 형태를 바꾸는 것 (결정 필요)

### ★ 결정 1 — CLI 연동을 MCP 서버로

**우리 현재 설계 (PLAN.md §7):**
격리 임시 디렉터리를 만들고 → 필요한 파일을 복사해 넣고 → CLI를 실행하고 →
stdout에서 펜스드 JSON 블록을 파싱한다.

**graphify 방식:**
지식 베이스를 **MCP 서버로 노출**한다. `python -m graphify.serve graph.json`.
도구: `query_graph`, `get_node`, `get_neighbors`, `shortest_path`.
stdio 전송(개인용) 또는 **HTTP 전송(팀 공용)**.

MCP 쪽이 나은 이유:

| | 파일 복사 방식 | MCP 방식 |
|---|---|---|
| 컨텍스트 | 우리가 "필요할 것 같은" 파일을 **밀어 넣음.** 과잉 또는 부족 | 에이전트가 필요한 것만 **당겨 감** |
| 왕복 | 1회. 부족하면 실패 | 필요한 만큼 탐색 |
| 출력 파싱 | CLI 3종의 stdout 포맷 차이를 흡수해야 함 | 도구 호출은 **구조화된 규약**. 파싱 없음 |
| 토큰 | 밀어 넣은 만큼 전부 과금 | 실제 읽은 것만 |
| 지원 | — | Claude Code · Gemini CLI · Codex **셋 다 MCP 지원** |

**그리고 이게 CO-Hub와 맞물립니다.** graphify의 `--transport http --api-key`는
"팀 전체가 하나의 URL을 바라보고, 각자 로컬 설치가 필요 없게" 하려는 설계입니다.
우리 CO-Hub가 정확히 그 자리에 있습니다 — 허브가 **동기화 API + MCP 엔드포인트**를
동시에 제공하면, 동료의 CLI가 사내 위키를 네이티브 도구로 씁니다.

**단점:** MCP 서버가 새 서브시스템입니다. 그리고 쓰기 경로(ChangeSet 생성)는 여전히
CLI 실행 + JSON 회수가 필요합니다 — MCP는 **읽기 경로를 대체**하지 쓰기를 대체하지 않습니다.
즉 두 경로를 다 만들어야 합니다.

**권장: 채택.** 단 M3(질의) 이후로 미루고, M2(인제스트)는 현재 방식 유지.
질의는 탐색적이라 MCP 이득이 크고, 인제스트는 입력이 정해져 있어 이득이 작습니다.

### ★ 결정 2 — 그래프/커뮤니티 분석 계층을 넣을 것인가

graphify가 그래프에서 뽑아내는 것들:

- **커뮤니티 탐지 (Leiden)** — 위키가 실제로 어떤 하위 주제로 갈라져 있는지.
  **임베딩 불필요** — 링크 구조 자체가 유사도 신호
- **God nodes** — 가장 많이 연결된 개념. "모든 게 이걸 통과한다"
- **Surprising connections** — 서로 다른 클러스터에 사는 것들 사이의 링크를
  **의외성 순으로 정렬**. 이건 우리에게 **없던 기능**이고, "통찰"에 해당합니다
- **Suggested questions** — 이 지식 베이스만이 답할 수 있는 질문 4~5개

우리가 이미 가진 것: 위키링크 그래프(Obsidian 호환이라 자동으로 존재).
**저장 계층을 새로 만들 필요가 없습니다.** 링크를 순회해 분석만 하면 됩니다.

Lint와도 겹칩니다 — 고아 페이지(#3)와 누락 상호참조(#5)는 이 분석의 부산물입니다.
지금 계획은 그걸 LLM에게 물어보게 돼 있는데, **그래프로 계산하는 게 정확하고 공짜입니다.**

**단점 — 정직하게:** graphify는 Python이고 우리는 Electron/TS입니다.
MinHash/LSH, Jaro-Winkler, Leiden을 TS로 다시 만들어야 합니다.
JS 생태계에는 Leiden이 아니라 **Louvain**만 있는 것으로 보이며(`graphology-communities-louvain`),
이건 **확인이 필요합니다**. 대안은 Python 사이드카 번들인데 설치본이 커지고
사내 배포가 복잡해집니다.

**권장: 채택하되 축소.** M4에서 링크 그래프 분석(커뮤니티·god node·고아·의외의 연결)까지만
TS로 구현하고, dedup의 MinHash/LSH는 **위키 규모가 수백 페이지를 넘을 때** 도입합니다.
그 전까지는 정규화 + Jaro-Winkler만으로 충분합니다 (후보쌍이 적어 O(n²)가 문제되지 않음).

## 3. 그대로 가져올 운영 디테일

| 항목 | graphify | 우리 적용 |
|---|---|---|
| PreToolUse 훅 | Claude Code·Gemini CLI에서 원시 파일 읽기 전에 훅이 발동해 그래프 사용을 유도. `--strict`는 세션 첫 원시 읽기를 **차단**하고 이후 되돌림 | 우리 `AGENTS.md` 포인터 파일보다 강한 방식. 채택 |
| **Codex 훅 제약** | Codex Desktop이 `PreToolUse`의 `hookSpecificOutput.additionalContext`를 **거부**함. graphify는 Codex 훅을 **의도적 no-op**으로 두고 `AGENTS.md`에 의존 | **M0에서 태울 시간을 아껴 줌.** Codex는 지시 파일 방식으로 확정 |

## 5. 벤치마크에 대한 주의

README의 수치는 **자체 보고**이며 우리 워크로드의 예측치가 아닙니다. 정확히 옮기면:

| 벤치마크 | graphify | 비교 대상 |
|---|---|---|
| LOCOMO (n=300) recall@10 | **0.497** | mem0 0.048, supermemory 0.149 |
| LOCOMO (n=300) QA 정확도 | 45.3% | **supermemory 49.7%** (더 높음), mem0 27.3% |
| LongMemEval-S (n=50) QA | 76% | dense RAG와 **동률** |
| 그래프 빌드 LLM 크레딧 | **0** | 대부분의 시스템은 토큰 과금 |

QA 정확도는 supermemory보다 **낮습니다.** recall이 높다고 QA가 높은 게 아닙니다.
"71.5배 토큰 절감"도 특정 코퍼스(52파일) 자체 측정이며, 6파일에서는 **약 1배**
(절감 없음)라고 스스로 밝힙니다.

우리에게 유의미한 시사점은 순위표가 아니라 **"구조화된 그래프를 먼저 만들어 두면
질의당 토큰이 줄고, 그 절감은 코퍼스가 커질수록 커진다"** 는 방향성입니다.
우리 CLI 호출이 비용 중심이므로 방향은 맞습니다. 배수는 인용하지 않습니다.
