## 1. CLI 비대화형 규약 (항목 1·3)

검증 환경: Linux, Claude Code 2.1.259 / Gemini CLI 0.58.0 / Codex CLI 0.153.2.
**Windows에서 재확인 필요** (§8).

### 1.1 3종 비교

| | Claude Code | Gemini CLI | Codex |
|---|---|---|---|
| 비대화형 | `-p` / `--print` | `-p` / `--prompt` | `codex exec` |
| JSON 출력 | `--output-format json\|stream-json` | `-o json\|stream-json` | `--json` (JSONL) |
| **스키마 강제** | **`--json-schema <문자열>`** | **없음** | **`--output-schema <파일>`** |
| 자동 승인 | `--permission-mode dontAsk` | `-y` / `--approval-mode yolo` | `--dangerously-bypass-...` |
| 읽기 전용 모드 | `--permission-mode plan` | `--approval-mode plan` | `-s`(sandbox) |
| 세션 재개 | `--resume <id>` | `--session-file` | `codex exec resume` |
| 도구 제한 | `--disallowedTools` | `-e`(확장 선택) | `-c` 설정 |
| MCP | `claude mcp add` + `--mcp-config` | `gemini mcp add` | `codex mcp add` |
| 지시 파일 | `CLAUDE.md` | **`GEMINI.md`** | `AGENTS.md` |

### 1.2 `--json-schema`가 §7.1 설계를 대체한다

계획서 §7.1은 "stdout에서 **단일 펜스드 ```json 블록**을 회수한다"였습니다. **불필요합니다.**

실측: `--output-format json`으로 받은 응답에 **`structured_output` 키가 이미 파싱된 객체**로
들어 있습니다. 스크래핑도, 이중 파싱도 없습니다.

```
top-level keys: type, subtype, is_error, num_turns, duration_ms,
                total_cost_usd, usage, modelUsage, stop_reason,
                permission_denials, session_id, result, structured_output
```

`result`는 JSON 문자열, `structured_output`은 **파싱된 dict**. 어댑터는 후자만 읽으면 됩니다.

**CLI별 등급이 갈립니다:**

| 등급 | CLI | 처리 |
|---|---|---|
| A — 스키마 강제 | Claude Code, Codex | 구조 검증을 CLI가 보장 |
| B — 강제 불가 | Gemini | 펜스드 블록 파싱 + 앱에서 JSON Schema 검증. 실패 시 1회 재요청 |

Gemini만 §7.1의 원래 설계가 필요합니다. 어댑터 인터페이스에 `supportsSchema: boolean`을 추가합니다.

### 1.3 ★ 비용 구조 — 계획에 없던 발견

실제 인제스트를 3회 돌려 측정했습니다 (모델 `claude-sonnet-5`, 4줄짜리 한국어 회의록).

| 조건 | 턴 | cache 생성 | cache 읽기 | 출력 | 비용 | 시간 |
|---|---|---|---|---|---|---|
| 기본 (파일 탐색 허용) | 8 | 34,506 | 66,087 | 2,476 | **$0.176** | 24s |
| 도구 차단 + 내용 인라인 | 2 | 29,747 | 0 | 1,054 | **$0.130** | 10s |
| 위 + **세션 재개** | 2 | 1,713 | **29,747** | 3,605 | **$0.049** | 40s |

**핵심: 문서 4줄을 넣는 데 $0.13이 듭니다.** 이 비용의 대부분은 우리 내용이 아니라
**Claude Code 자신의 시스템 프롬프트 + 도구 정의 약 3만 토큰**이고, 프로세스를 새로 띄울 때마다
cache **생성**으로 과금됩니다.

세션을 재개하면 같은 3만 토큰이 cache **읽기**로 바뀌어 **비용이 62% 떨어집니다.**

**설계 결론 (PLAN.md §4 반영 필요):**

> 인제스트는 **문서당 프로세스**가 아니라 **배치당 장기 세션**으로 돈다.
> 문서 100건을 1건씩 처리하면 고정 오버헤드만 약 $13. 10건씩 묶으면 약 $1.3.
> 계획서의 "일괄 모드"는 편의 기능이 아니라 **비용 구조상 기본값**이어야 한다.

⚠️ 이 수치는 sonnet-5 · 소형 문서 · Linux 기준의 **1회 측정**입니다. 절대값이 아니라
**비율(고정비가 지배한다)** 을 받아들여야 합니다.

### 1.4 부수 관찰

실측 출력에서 `path`가 `entities/에이콤(주).md`로 나왔습니다. 우리가 지시한 `wiki/entities/`

### 3.1 이메일 스레드 복원

입력 순서를 일부러 섞어(`mail-3 → mail-1 → mail-2`) 넣었는데 `In-Reply-To` / `References`만으로
정확히 복원했습니다.

```
계약 갱신 일정
  RE: 계약 갱신 일정
    RE: RE: 계약 갱신 일정
```

v0.2에서 놓쳤던 기능이고, LLM 없이 무료로 동작합니다.

### 3.2 xlsx 수식 의존 그래프

```
원가!B2 → 원가!D2     (D2 = B2*C2)
원가!C2 → 원가!D2
원가!D2:D3 → 원가!D4  (D4 = SUM(D2:D3))
원가!D4 → 요약!B1     ★ 시트 간 참조 (B1 = 원가!D4*1.1)
```

시트 간 참조까지 잡힙니다. "이 숫자가 어디서 왔나"에 답할 수 있습니다.

주의: 정규식 기반이라 `SUM(`, `IF(` 같은 함수명을 참조로 오인할 수 있습니다.
현재 구현은 뒤에 `(`가 오는 토큰을 배제해 회피했으나, **실제 사내 문서로 재검증 필요** (§8).

### 3.3 스캔 PDF 감지

임계 **10자/쪽**으로 분리됩니다 (정상 55.0 vs 스캔본 0.0). 다만 표지·간지가 많은 문서에서
오탐 가능성이 있으므로, **문서 전체 평균이 아니라 "텍스트 있는 쪽의 비율"** 로 판정하는 편이
안전합니다 — 실제 사내 스캔본으로 재보정 필요.

## 4. 한국어 엔티티 유사도 (항목 7)

테스트 쌍 19개 (병합돼야 함 11 / **절대 병합 금지 8**).
위키에서 오병합은 복구가 어려우므로 **오병합 0을 절대 조건**으로 두고 재현율을 최대화했습니다.

### 4.1 ★ graphify의 엔트로피 게이트는 한국어에서 작동하지 않는다

graphify는 "글자당 2.5비트 미만이면 퍼지 매칭 제외"로 짧은 약어를 거릅니다.
한국어에서는 **무력합니다**:

```
AI   len=2  H=1.00
DB   len=2  H=1.00
팀    len=1  H=0.00
```

전부 2.5비트 미만이라 통과할 것 같지만 — 문제는 반대입니다. 한글 음절은 알파벳 크기가 커서
**짧아도 엔트로피가 높게 나올 수 있어** 게이트가 뚫립니다.

**수정: 엔트로피 단독이 아니라 `길이 ≥ 3 AND 엔트로피 ≥ 1.0`.**
이 조합으로 위 7개를 전부 차단했습니다.

### 4.2 ★ 자모 분해는 오히려 해롭다

한글 음절은 원자가 아니므로 자모로 펴면 나아질 것이라 예상했습니다. **틀렸습니다.**

```
자모   임계  TP FP TN FN   정밀도  재현율
미적용 0.92  10  3  5  1   0.769   0.909
미적용 0.96  10  0  8  1   1.000   0.909   ← 채택
적용   0.92  11  4  4  0   0.733   1.000
적용   0.96  11  1  7  0   0.917   1.000
```

자모 분해는 **모든 임계값에서 오병합이 같거나 더 많습니다.** 분해하면 서로 다른 단어가
모음·종성을 공유해 더 비슷해 보이기 때문입니다. 채택하지 않습니다.

### 4.3 ★ graphify의 임계 0.92는 한국어에서 오병합 3건

```
0.92 → 오병합 3건 (에이콤|에이스콤, 김철수|김영수, 구매팀|구매팀장 류)
0.96 → 오병합 0건
```

**한국어에서는 0.96이 필요합니다.** 차용한 파라미터를 그대로 쓰면 안 됩니다.

### 4.4 채택 설정

```
정규화   NFKC + 법인격 접미사 제거((주)/주식회사/Inc./Corp.) + 조사 제거 + 공백/구두점 제거
게이트   길이 ≥ 3 AND 글자당 엔트로피 ≥ 1.0
유사도   Jaro-Winkler (자모 분해 없음)
임계     0.96
결과     정밀도 1.000 · 재현율 0.909 · 오병합 0건
```

자동으로 못 잡는 것 (사람이 직접 병합):

```
데이타베이스 | 데이터베이스   (외래어 표기 흔들림)  0.911
```

⚠️ **테스트 쌍 19개는 작습니다.** 방향성 결과이지 검증된 수치가 아닙니다.
실제 사내 문서에서 엔티티명 100쌍 이상을 모아 재측정해야 합니다 (§8).

고아 페이지     정답 2장 → 검출 2장, 완전 일치      ← Lint #3을 LLM 없이 계산

10,000노드 100,000간선 → 65ms
```

위키 규모에서 성능은 전혀 문제가 아닙니다. **Lint #3(고아)·#5(누락 상호참조)를 LLM 질의에서

허브 노드는 모든 것과 이웃이 안 겹쳐서 **무조건 의외성 상위에 올라옵니다.**

```
상위 3개 중 정답 포착 — 허브 미제외 1/3  vs  허브 제외 3/3
```

**보정: 연결 수 상위 10% 노드를 의외성 순위에서 제외.** graphify에 `--exclude-hubs` 옵션이
왜 있는지 이 측정으로 이해했습니다.

## 6. 허브 규모 산정 (항목 9)

가정: 원본 500건, 원본당 12페이지 접촉, 신규 비율 25%, 페이지당 8개정.
페이지 크기는 가정값 대신 **실제 한국어 위키 페이지를 만들어 측정**(1,114 B, gzip 682 B).

```
위키 페이지        1,500장
pages              1.6 MB
page_versions     12.7 MB   (8개정)
events             1.2 MB
─────────────────────────
DB 합계           15.5 MB

blob 합계          2.83 GB   (일반 500건 900MB + 대형 10건 1.95GB)
```

**결론 3가지**

1. DB 15.5MB — `HUB.md`의 "수십 MB" 예상과 부합. **전 버전 보관에 아무 문제 없습니다.**
2. blob이 DB의 **187배**. → `HUB.md` §7의 디스크 경고는 **blob 기준**으로 걸어야 합니다.
3. 클라이언트 첫 동기화(페이지만, blob 제외) 전송량 **1.6MB** → 사내망에서 수 초.
   지연 blob 다운로드 설계가 옳았습니다.

개정 횟수 민감도:

```
 4개정 →  9.2 MB      32개정 →  53.8 MB
 8개정 → 15.5 MB      64개정 → 104.8 MB
16개정 → 28.3 MB
```

**개정 64회까지 가도 1GB 미만. 버전 정리 정책은 v1에 불필요합니다.**
