# co-secondbrain — 프로젝트 단위 Second Brain 프레임워크

> Windows 데스크톱 앱. 이메일·회의 전사·Word·Excel·PowerPoint·PDF·Markdown을 받아
> LLM이 **점진적으로 위키를 짓고 유지**한다.
> 개인 로컬 세컨브레인이 기본이고, 프로젝트 단위 **CO 영역**은 사내 로컬 서버를 통해
> 동료와 주고받는다.

상태: **계획 v0.3**. 코드 없음.

- 기반 패턴: Karpathy "LLM Wiki" — 원문 전문 확인 후 반영.
  정리본 [`REFERENCE-llm-wiki.md`](REFERENCE-llm-wiki.md), 변형 내역은 그 문서 §9
- 선행 사례 검토: [`REVIEW-graphify.md`](REVIEW-graphify.md) — v0.3의 §4·§6·§7·§8 변경 근거
- 서버 설계: [`HUB.md`](HUB.md)
- 디자인: [`DESIGN-SYSTEM.md`](DESIGN-SYSTEM.md)

## 2. 두 개의 공간 — 개인과 CO

```
%USERPROFILE%\SecondBrain\
│
├─ personal/                    ← 개인 세컨브레인 (기본)
│   └─ 외부로 나가지 않음. LLM CLI에만 필요한 만큼 전달됨
│
└─ projects/
    ├─ ACME/                    ← CO 영역: 허브 공간의 로컬 미러
    └─ BETA/
```

두 공간의 **내부 구조는 완전히 동일**합니다. 같은 엔진, 같은 인제스트, 같은 질의.
차이는 **동기화 대상이 있느냐**뿐입니다.

### 공간 사이의 두 가지 명시적 행위

동기화는 자동으로 일어나지 않습니다. 사람이 고릅니다.

| 행위 | 방향 | 내용 |
|---|---|---|
| **Contribute** | 개인 → CO | 공유될 내용을 전문으로 보여주는 검토 화면 필수 경유. 실수로 사적 메모가 나가는 것을 막는 유일한 장치 |
| **Adopt** | CO → 개인 | CO 페이지를 개인 위키로 복제. `derived_from: co://ACME/entities/acme-corp@v12` 기록. 원본이 갱신되면 "채택본 낡음" 배지 |

CO 영역에 원본을 **직접 인제스트**하는 것도 가능합니다(업무 문서는 대개 이쪽).

### 링크 방향 규칙

- 개인 → CO 링크: **허용** (`[[co:ACME/엔티티/에이콤]]`)
- CO → 개인 링크: **금지.** 저장 전 검증기가 차단

금지 이유: 동료에겐 영원히 깨진 링크이고, "누군가의 사적 페이지가 존재한다"는 사실 자체가
새어 나갑니다.

## 3. Vault 내부 구조

```
<Space>/
├─ sources/                     # 원본. 앱이 절대 수정하지 않음
├─ extracted/                   # 결정론적 추출. LLM 미개입. 언제든 재생성
│   ├─ <name>.md                #   본문 텍스트
│   ├─ <name>.anchors.json      #   페이지/슬라이드/셀/타임코드 좌표
│   └─ <name>.structure.json    #   ★ 구조 관계 (§6.2)
│
├─ wiki/                        # ★ LLM 소유. Obsidian 호환 마크다운
│   ├─ overview.md
│   ├─ sources/  entities/  concepts/  synthesis/
│
├─ assets/                      # 이미지 (Obsidian 첨부 폴더 규약)
├─ schema/
│   ├─ AGENTS.md                # ★ 정본 스키마
│   └─ taxonomy.md
├─ index.md                     # 카탈로그 (§5)
├─ log.md                       # 시간순 추가 전용 (§5)
├─ .sbignore                    # 무시 규칙 (§9.3)
│
└─ .sb/                         # 앱 내부. 위키가 아님
    ├─ config.json
    ├─ catalog.sqlite           # FTS5 + 링크 그래프 캐시. 재생성 가능
    ├─ cache/                   # ★ 시맨틱 캐시 (§9.1)
    ├─ manifest.json            # ★ 성공 완료 시에만 기록 (§9.1)
    ├─ history/                 # 스냅샷
    └─ sync/                    # CO 영역만
```

### 설계 원칙 5가지

1. **디스크가 진실이다.** SQLite는 재생성 가능한 캐시. 앱을 지워도 지식은 마크다운으로 남는다.
2. **Obsidian 호환을 유지한다.** wikilink `[[ ]]`, YAML front-matter, 고정 첨부 폴더.
   앱은 Obsidian을 **대체**하지만 **배제하지 않는다.**
3. **LLM은 디스크에 직접 쓰지 않는다.** ChangeSet을 내고 사람이 diff로 승인하면 앱이 적용한다.
4. **모든 주장에 앵커 인용과 신뢰도 태그.** §3.1.
5. **스키마는 공동 진화한다.** 앱에 스키마 편집기가 있고, LLM이 개정을 제안할 수 있다.

### 3.1 신뢰도 — 3분류 + 이산 루브릭

v0.2의 `confidence: high | medium | low`는 **의미가 모호해 폐기**합니다.
"high"가 무슨 뜻인지 사람마다 다르게 읽힙니다. 대신 **인식론적으로 명확한** 3분류를
**페이지가 아니라 주장 단위**로 답니다. (근거: `REVIEW-graphify.md` §1.A)

| 태그 | 의미 | 처리 |
|---|---|---|
| `EXTRACTED` | 원본에 **명시**돼 있음 | 기본. 배지 없음 |
| `INFERRED` | 모델의 추론. 점수 동반 | 점수에 따라 표시 |
| `AMBIGUOUS` | 불확실 | **Lint 결과함으로 자동 라우팅** |

`INFERRED`의 점수는 자유 실수가 아니라 **다섯 개 중 택일**입니다.
모델에게 "0~1 사이로 매겨라"라고 하면 뭉개진 값이 나오고, 고르라고 하면 일관됩니다.

```
0.95  거의 확실 — 명시적 교차 참조, 타당한 대상이 하나뿐
0.85  강한 근거 — 명명과 맥락이 일치
0.75  타당함    — 맥락상 그럴듯하나 명시적이지 않음
0.65  약함      — 이름 유사성뿐
0.55  추측
```

업무 위키에서 "계약 갱신일은 2027-01이다"가 계약서에 적혀 있는지(EXTRACTED)
메일 정황으로 추론한 것인지(INFERRED 0.75)는 결정적으로 다릅니다.

### front-matter 계약

```yaml
---
id: ent-acme-corp
type: entity              # source | entity | concept | synthesis | overview
title: 에이콤(주)
summary: 2026년 킥오프의 주 협력사. 계약 갱신일에 문서 간 불일치 있음.   # 300자 상한
aliases: [Acme, ACME, 에이콤]      # Lint #9가 후보를 제안, 사람이 승인
tags: [협력사, 계약]
claims:                            # ★ 주장 단위 신뢰도
  - text: 계약 갱신일은 2027-01-15
    source: src-2026-09-03-kickoff#slide-12
    confidence: EXTRACTED
  - text: 갱신 협상 주체는 구매팀
    source: src-2026-08-20-mail-a41f#body
    confidence: INFERRED
    score: 0.75
open_questions:
  - 계약 갱신일이 문서마다 다름 (2027-01 vs 2027-03)
derived_from: null        # CO 페이지를 채택한 경우 co://ACME/...@v12
updated: 2026-09-03T10:22:00+09:00
updated_by: hong@corp
---
```

`summary`가 있는 이유: 원문의 index.md 형식이 "링크 + 한 줄 요약 + 메타"이기 때문입니다.
**요약은 LLM이 씁니다.** 앱은 그것을 모아 index.md를 조립할 뿐입니다.
300자 상한은 index.md가 비대해지는 것을 막습니다.

## 4. 세 가지 동작

### Ingest

```
파일 드롭
  → ① 텍스트 추출 + 앵커 부여                    (로컬, 무료)
  → ② ★구조 추출 — 스레드·제목트리·셀참조 등     (로컬, 무료, EXTRACTED)
  → ③ 시맨틱 캐시 조회 — 변경분만 통과            (§9.1)
  → ④ 관련 위키 페이지 선별 (FTS + 별칭 + 링크그래프)
  → ⑤ LLM CLI 실행 → ChangeSet 생성
  → ⑥ ★요점 논의 / diff 검토 화면
  → ⑦ 적용: 파일 쓰기 → index.md 재조립 → log.md 추가 → 스냅샷
```

②가 v0.3에서 새로 들어간 단계입니다. v0.2는 구조까지 전부 LLM에 맡기고 있었는데,
**문서에는 공짜로 뽑을 수 있는 구조가 많습니다.** §6.2 참조.
이 단계의 산출물은 전부 `EXTRACTED`이므로 LLM이 그 위에 추론만 얹으면 됩니다.

원문 흐름의 6단계(읽기 → 요점 논의 → 요약 → 인덱스 → 관련 페이지 → 로그)를 전부 유지합니다.
원본 1건이 페이지 10~15개를 건드릴 수 있습니다.

**두 가지 모드** (원문이 둘 다 인정):

- **감독 모드** (기본) — 한 건씩. 요약을 읽고 강조점을 지시하고 페이지별 승인
- **일괄 모드** — 여러 건을 한 번에. 검토는 마지막에 묶어서. 백로그 정리용

어느 쪽을 쓸지는 `schema/AGENTS.md`에 기록합니다.

### Query

```
질문 → index.md 먼저 읽음 → 후보 페이지 선별 (FTS5 + 링크 그래프)
     → LLM이 인용 붙여 답변 → [위키에 보관] → synthesis/ 페이지
```

| 출력 형식 | v1 | 비고 |
|---|---|---|
| 마크다운 페이지 · 비교 표 | ✓ | |
| 슬라이드 덱 (Marp) | ✓ | 마크다운이라 추가 의존성 없음 |
| 차트 (matplotlib) | ✗ v2 | 사내 PC에 Python 보장 불가 |
| 캔버스 | ✗ v2 | |

### Lint

**계산 검사**(LLM 없이 앱이 판정)와 **판단 검사**(LLM 필요)를 분리합니다.
v0.2는 #3·#5를 LLM에게 물어보게 돼 있었는데, **그래프로 계산하는 쪽이 정확하고 공짜입니다.**

| # | 검사 | 방식 | 출처 |
|---|---|---|---|
| 1 | 페이지 간 모순 | LLM | 원문 |
| 2 | 새 원본이 대체한 낡은 주장 | LLM | 원문 |
| 3 | 인바운드 링크 없는 고아 페이지 | **계산** | 원문 |
| 4 | 언급되지만 자기 페이지가 없는 개념 | LLM | 원문 |
| 5 | 누락된 상호 참조 | **계산** | 원문 |
| 6 | 데이터 공백 → 찾아볼 원본 제안 | LLM | 원문(웹 검색)을 사내망에 맞게 조정 |
| 7 | 출처 없는 주장 | **계산** | 추가 |
| 8 | 깨진 앵커 (원본 교체로 번호 불일치) | **계산** | 추가 |
| 9 | **엔티티 중복 후보** | **계산** + 애매 구간만 LLM | graphify |
| 10 | `AMBIGUOUS` 주장 누적 | **계산** | 추가 |

계산 검사 6종은 즉시·무료로 돌고, LLM은 4종만 판단합니다.
모든 결과는 인제스트와 동일한 diff 검토를 거칩니다.

**#9 엔티티 중복** — v0.2의 가장 큰 구멍이었습니다. 시간이 지나면 위키가
`에이콤(주)` / `Acme` / `ACME Corp` / `에이콤`을 서로 다른 페이지 4개로 갖게 되는데,
`aliases:` 필드는 만들어 뒀지만 **그걸 채우는 절차가 없었습니다.** §8.2.

## 5. index.md 와 log.md

**index.md** — 콘텐츠 지향 카탈로그. 질의 시 **가장 먼저 읽는 파일**.
LLM이 매번 다시 쓰는 대신 **앱이 front-matter의 `summary`에서 조립**합니다.
내용의 저자는 여전히 LLM이고, 조립만 결정론적이라 본문과 어긋날 수 없습니다.

```markdown
## 엔티티
- [[entities/acme-corp|에이콤(주)]] — 2026년 킥오프의 주 협력사. 계약 갱신일 불일치. `원본 4 · 2026-09-03`
```

**log.md** — 시간순 추가 전용. **원문이 제시한 접두사 형식 그대로:**

```markdown
## [2026-09-03] ingest | 킥오프 발표.pptx
## [2026-09-03] query  | 계약 갱신일이 언제인가
## [2026-09-04] lint   | 모순 2건, 고아 3건, 중복 후보 1건
```

`grep "^## \[" log.md | tail -5`로 최근 이력이 나옵니다.
CO 영역에서는 허브 DB의 events가 정본이고, log.md는 동기화 시 재생성됩니다.

## 6. 추출

### 6.1 텍스트 + 앵커 (전부 로컬)

| 형식 | 후보 라이브러리 | 앵커 |
|---|---|---|
| `.docx` | `mammoth` | 제목 경로 |
| `.xlsx` `.csv` | `exceljs` / `xlsx` | `시트!A1:D20` |
| `.pptx` | unzip + `fast-xml-parser` | 슬라이드 번호 + 발표자 노트 |
| `.pdf` | `pdfjs-dist` | 페이지 번호 |
| `.msg` | `@kenjiuno/msgreader` | message-id / 스레드 |
| `.eml` | `mailparser` | message-id / 스레드 |
| `.srt` `.vtt` `.txt` | 자체 파서 | 타임코드 + 화자 턴 |
| `.md` | 직접 | 제목 경로 |

### 6.2 ★ 구조 추출 — LLM 없이 뽑는 관계

전부 `EXTRACTED` 신뢰도로 `<name>.structure.json`에 기록됩니다.

| 형식 | 뽑는 것 |
|---|---|
| **이메일** | **`In-Reply-To` / `References` 헤더로 스레드 트리 복원** (RFC 5322). 발신자↔수신자 그래프, 시간 순서 |
| `.xlsx` | 시트→표→열 구조, **수식의 셀 참조 = 의존 그래프**, 명명 범위 |
| `.docx` | 제목 트리(H1>H2>H3), 각주, 상호참조 필드, 주석 |
| `.pptx` | 슬라이드 순서, 제목 계층, 발표자 노트, 도형 그룹 |
| `.pdf` | 목차(북마크), 내부 링크, 각주 |
| 전사 | 화자 턴, 발언 인접 관계 |
| `.md` | `[[wikilink]]`, `[text](./other.md)` → `references` 엣지 |

**이메일 스레드 복원을 v0.2에서 완전히 놓치고 있었습니다.** 이메일은 우리 입력 형식 중
하나이고 스레드는 그 자체로 지식 구조인데, 표준 헤더로 공짜로 복원됩니다.

**xlsx 수식의 셀 참조**도 마찬가지입니다. "이 숫자가 어디서 왔나"는 업무에서 가장 자주
나오는 질문이고, 수식 그래프가 그 답입니다.

### 6.3 이미지

원문의 지적을 반영합니다: LLM은 인라인 이미지가 든 마크다운을 한 번에 읽지 못합니다.
추출기는 이미지를 `assets/`에 떼어내고 본문에는 참조만 남깁니다.
LLM은 텍스트를 먼저 읽고, 필요한 이미지만 **별도 턴에서** 봅니다.

### 6.4 알려진 한계 (v1에 남김)

- 스캔 PDF는 텍스트 레이어가 없습니다. 0자 감지 후 "OCR 필요" 경고. OCR은 v2
- 표가 많은 PDF는 열 구조가 뭉갭니다. 원문 뷰어 점프로 보완
- 위 라이브러리는 **M0에서 실제 샘플로 검증**합니다

## 7. LLM CLI 어댑터 (3종)

```ts
interface AgentCli {
  id: 'claude-code' | 'gemini' | 'codex';
  detect(): Promise<{ found: boolean; path?: string; version?: string }>;
  supportsMcp(): Promise<boolean>;                       // M0 검증 대상
  run(job: { workdir: string; promptFile: string }): AsyncIterable<Chunk>;
}
```

### 7.1 쓰기 경로 (ChangeSet 생성) — 확정

1. 임시 **격리 작업 디렉터리**를 만든다
2. 이번 작업에 필요한 것만 복사한다 — `schema/AGENTS.md`, `index.md`,
   대상 `extracted/*`, 선별된 위키 페이지
3. CLI를 그 디렉터리에서 서브프로세스로 실행한다
4. stdout에서 **단일 펜스드 ```json 블록**으로 된 ChangeSet을 회수한다
5. 디렉터리를 폐기한다

격리하는 이유: Vault 루트를 통째로 주면 무관한 프로젝트 문서까지 컨텍스트에 올라가고,
앱이 어떤 파일이 전달됐는지 기록·통제할 수 없습니다.

**출력 계약을 ChangeSet JSON 한 덩어리로 고정**하는 것이 CLI 3종을 하나로 묶는 핵심입니다.
쓰기 경로는 MCP로 대체하지 않습니다 — 에이전트가 쓰기 도구를 직접 호출하게 되면
"사람 승인 전에는 디스크에 안 쓴다"는 원칙을 지키기 어렵습니다.

### 7.2 읽기 경로 (질의) — **M0 검증 후 결정**

두 안을 모두 기록해 두고 M0 결과로 확정합니다.

**안 A — 파일 복사 (현행 유지)**
쓰기 경로와 동일한 방식. 새 서브시스템 없음. 사내 정책 리스크 0.
단점: 필요할 것 같은 페이지를 **추측해서 밀어 넣어야** 하고, 안 읽힌 페이지까지 전송됩니다.

**안 B — 내장 MCP 서버**
앱에 **우리가 만든 MCP 서버를 내장**하고 CLI가 도구로 붙습니다.
`get_page` · `search` · `neighbors` · `path` 같은 읽기 전용 도구만 노출합니다.

```
[사용자 PC]  co-secondbrain.exe ─ 내장 MCP 서버   ← stdio 또는 127.0.0.1
                    ↕
             claude.exe  ─────────────────────▶  api.anthropic.com   ← 외부는 여기뿐

[사내서버]   co-hub.exe ─ MCP HTTP 엔드포인트     ← 사내 IP. 인터넷 아님
```

**외부 연동이 아닙니다.** MCP는 프로토콜이지 서비스가 아니며, 서버는 우리 실행 파일의
일부입니다. 외부로 나가는 경로는 지금과 동일하게 `CLI → api.anthropic.com` 하나뿐입니다.

오히려 **전송량이 줄어듭니다** — 에이전트가 필요한 페이지만 당겨 가므로 안 읽은 페이지는
전송되지 않습니다.

| | 안 A 파일 복사 | 안 B MCP |
|---|---|---|
| 컨텍스트 | 우리가 추측해 **밀어 넣음** | 에이전트가 **당겨 감** |
| 왕복 | 1회. 부족하면 실패 | 필요한 만큼 탐색 |
| 출력 파싱 | CLI 3종 stdout 차이 흡수 | 구조화된 도구 규약 |
| 전송량 | 밀어 넣은 만큼 전부 | 실제 읽은 것만 |
| 사내 정책 리스크 | 없음 | **MCP 등록 자체가 막혀 있을 수 있음** |

**M0 검증 항목:** ① 사내 정책상 `claude mcp add`가 실제로 되는지
② Gemini CLI · Codex의 MCP 지원 수준. Claude Code는 지원이 확실하지만 나머지 둘은
**확실하지 않습니다.** 셋 중 일부만 되면 **그 CLI만 안 A로 폴백**합니다 — 어댑터 구조라
국소 변경입니다.

### 7.3 스키마 파일 이름

정본은 `schema/AGENTS.md` 하나이고, 격리 작업 디렉터리에 각 CLI가 찾는 이름으로
포인터 파일을 생성합니다.

| CLI | 규약 파일명 | 근거 |
|---|---|---|
| Claude Code | `CLAUDE.md` | gist 원문 명시 |
| Codex | `AGENTS.md` | gist 원문 명시 |
| Gemini CLI | `GEMINI.md` | graphify가 `--platform gemini`로 지원. M0 재확인 |

**Codex 훅 제약 (graphify가 확인한 사실):** Codex Desktop은 `PreToolUse`의
`hookSpecificOutput.additionalContext`를 **거부**합니다. graphify는 Codex 훅을
의도적 no-op으로 두고 `AGENTS.md`에 의존합니다. 우리도 **Codex는 지시 파일 방식으로 확정**
하고 M0에서 시간을 태우지 않습니다.

Claude Code와 Gemini CLI는 `PreToolUse` 훅이 동작하므로, 에이전트가 원시 파일을 읽으려 할 때
위키 경로로 유도하는 훅을 설치합니다.

### ChangeSet 형식

```json
{
  "summary": "킥오프 발표에서 협력사 3곳과 마일스톤 5개를 확인",
  "discussion": "계약 갱신일이 8월 메일과 어긋납니다. 어느 쪽이 최신입니까?",
  "ops": [
    { "op": "create", "path": "wiki/entities/acme-corp.md",
      "baseHash": null, "content": "---\nid: ent-acme-corp\n..." },
    { "op": "update", "path": "wiki/concepts/contract-renewal.md",
      "baseHash": "sha256:9f2a...", "content": "..." }
  ]
}
```

`baseHash`가 낙관적 동시성의 기반입니다 (§10.4).

## 8. 그래프 분석 계층 (축소 도입)

### 8.1 링크 그래프 분석 — M4

우리는 **이미 그래프를 갖고 있습니다.** Obsidian 호환이라 wikilink가 그대로 간선입니다.
**새 저장 계층이 필요 없고**, 순회해서 분석만 하면 됩니다.

| 산출 | 내용 |
|---|---|
| **커뮤니티** | 위키가 실제로 어떤 하위 주제로 갈라져 있는지. **임베딩 불필요** — 링크 구조 자체가 유사도 신호 |
| **God node** | 가장 많이 연결된 개념. "모든 게 이걸 통과한다" |
| **고아 페이지** | Lint #3을 여기서 계산 |
| **누락 상호참조** | Lint #5를 여기서 계산 |
| **의외의 연결** | 서로 다른 커뮤니티에 사는 것들 사이의 링크를 **의외성 순으로 정렬.** v0.2에 없던 기능이고 "통찰"에 해당 |
| **제안 질문** | 이 위키만이 답할 수 있는 질문 4~5개 |

⚠️ **미검증:** JS 생태계에는 Leiden이 아니라 **Louvain**만 있는 것으로 보입니다
(`graphology-communities-louvain`). **M0에서 확인**하고, Louvain으로 충분한지 판단합니다.
커뮤니티 품질이 다소 떨어져도 우리 용도(주제 묶음 표시, 의외성 계산)에는 무리가 없을
가능성이 높습니다 — **추측입니다.**

### 8.2 엔티티 중복 제거 — 단계적

**지금 넣을 것 (M4):**

```
1. 정확 정규화        대소문자·공백·괄호·법인격 접미사(주식회사/(주)/Inc.)
2. ★엔트로피 게이트   글자당 2.5비트 미만 라벨은 퍼지 매칭 제외
                      ("AI", "DB", "PM" 같은 짧은 이름은 자동 병합이 위험
3. Jaro-Winkler       0.92 이상에서 후보 제시
4. 커뮤니티 보정      같은 클러스터면 가중
5. ★사람 승인         병합은 diff 검토를 거침. 자동 병합 없음
```

**보류 (위키가 수백 페이지를 넘을 때):** MinHash + LSH 블로킹.
후보쌍이 적은 동안은 O(n²) Jaro-Winkler로 충분합니다. 규모가 커지면 도입합니다.

**2단계 엔트로피 게이트가 이 설계를 안전하게 만드는 부분입니다.** 짧은 이름을 자동
병합하면 서로 다른 개념이 합쳐지고, 위키에서 그건 복구가 어렵습니다.

⚠️ **미검증:** 문자 n-gram 기반 유사도는 라틴 문자 기준 설계입니다.
**한국어 엔티티명 정확도는 M0에서 실측해야 합니다** — 조사 결합("에이콤이", "에이콤은")과
띄어쓰기 변형이 관건입니다. 필요하면 조사 제거 전처리를 넣습니다.

## 9. 운영 설계

### 9.1 시맨틱 캐시 + manifest

파일마다 **SHA256 콘텐츠 해시**로 LLM 추출 결과를 캐싱합니다. 재실행 시 변경분만 CLI에
보냅니다. **파일 이름이 바뀌면 캐시된 결과의 경로만 갱신**하고 재추출하지 않습니다.

**`manifest.json`은 성공적으로 완료됐을 때만 씁니다.** 실행 중 크래시가 나도 다음 실행의
diff가 오염되지 않습니다.

### 9.2 보안 단일 관문

모든 외부 입력이 `security.ts` 한 곳을 통과합니다.

| 함수 | 역할 |
|---|---|
| `sanitizeTitle` | **LLM이 쓴 페이지 제목이 곧 파일 이름이 됩니다.** 제어문자·경로 구분자·`..` 제거, Windows 예약어(`CON` `PRN` `NUL` `AUX` `COM1`…) 처리, 길이 상한 |
| `validateVaultPath` | 모든 쓰기 경로가 Vault 안으로 resolve되는지 |
| `validateHubUrl` | 허브 URL이 사설 IP 대역인지 |
| `capBlobSize` | 업로드 크기 상한 |

`sanitizeTitle`을 v0.2에서 놓쳤습니다. 모델이 `../../../Windows/System32/...` 같은 제목을
내면 경로 탈출입니다.

### 9.3 `.sbignore`

`.gitignore`와 같은 문법(`!` 부정 포함), 하위 디렉터리 스코프도 동일.
**추가로 제외만 할 뿐 다시 포함시키지는 않습니다.**
`sources/`를 네트워크 공유에 걸 때 필요합니다.

### 9.4 비용 상한

인제스트 작업 하나가 조용히 비용을 폭증시키지 않도록 상한을 둡니다.

- 작업당 최대 CLI 호출 횟수 (기본 3)
- 잘린 응답의 재귀 이분 재시도 깊이 상한 (기본 2, `0`이면 재시도 없음)
- 상한 도달 시 실패로 처리하고 사용자에게 표시. 조용한 재시도 없음

### 9.5 쿼리 로그는 기본 꺼짐

로컬 쿼리 로그는 **기본 비활성**입니다. 설정에서 명시적으로 켜야 하고,
끄기 설정이 항상 우선합니다. 회사 도구로서의 기본 자세입니다.

## 10. CO-Hub — 사내 로컬 서버

상세는 [`HUB.md`](HUB.md).

### 10.1 허브는 멍청하다 (의도적)

허브에 **LLM이 없습니다.** 인제스트·질의·린트는 전부 각자 PC의 CLI가 수행합니다.
허브는 페이지 버전 관리, blob 보관, 이벤트 로그, 토큰 확인만 합니다.

결과: 서버에 API 키가 없고, 서버가 죽어도 로컬 미러로 계속 일하고, 구형 사내 PC 한 대면
충분합니다.

### 10.2 무엇을 동기화하는가

| 대상 | 방식 |
|---|---|
| 위키 페이지 | 전량. 작고 텍스트라 빠름 |
| index.md / log.md | 안 함. 각 클라이언트가 재생성 |
| 원본 파일(blob) | **지연 다운로드.** 인용 클릭 또는 "오프라인 고정" 시에만 |
| extracted/ | 지연. 없으면 blob 받아 로컬 재추출 |
| 이벤트 로그 | 커서 기반 pull |

### 10.3 신원과 인증

허브 관리자가 사용자별 토큰을 발급하고, 앱은 Windows 자격 증명 관리자에 보관합니다.
`updated_by`가 토큰에서 나오므로 **귀속이 위조되지 않습니다.**

### 10.4 충돌 처리 — 잠금 없음

```
PUT /v1/spaces/ACME/pages/ent-acme-corp     If-Match: 12
  → 200  적용, 버전 13
  → 409  3-way 병합 재료(base / 서버) 동봉 → 병합 화면 → 재전송
```

서버가 버전을 강제하므로 파일 잠금·heartbeat 설계가 필요 없습니다.

### 10.5 MCP 엔드포인트 (§7.2 안 B 채택 시)

허브가 동기화 API와 **같은 프로세스·같은 토큰**으로 읽기 전용 MCP HTTP 엔드포인트를
제공합니다. 동료는 로컬 설치 없이 사내 URL만 바라보면 됩니다.
사내 IP 바인딩 + 토큰 필수. 인터넷 노출 없음.

### 10.6 오프라인

로컬 미러만으로 읽기·인제스트·질의·린트가 전부 됩니다. 변경은 `.sb/sync/pending`에 쌓이고
연결되면 push합니다.

### 10.7 남는 한계

- 접근 제어 단위는 **공간(프로젝트)**. 페이지 단위 권한 없음
- 허브는 단일 장애점. 백업은 DB 파일 + blob 디렉터리 복사
- 개인 금고는 동기화·백업 대상이 아님. 앱이 백업 미설정을 경고

## 11. 앱 구조

```
main (Node)                       renderer (React + TS)
├─ space/      공간 열기·감시      ├─ shell/      3-pane
├─ extract/    텍스트 + 구조 추출  ├─ ingest/     드롭 → 진행 → ★diff 검토
├─ index/      SQLite FTS5         ├─ wiki/       페이지 뷰·편집·그래프
├─ graph/      링크 그래프 분석    ├─ query/      질의 · 인용 · Marp
├─ agent/      CLI 어댑터 3종      ├─ lint/       점검 결과함
├─ mcp/        내장 MCP 서버(조건) ├─ sync/       기여 · 채택 · 병합
├─ changeset/  적용·충돌           └─ settings/   CLI · 허브 · 스키마 편집
├─ history/    스냅샷
├─ sync/       허브 클라이언트
├─ cache/      시맨틱 캐시
└─ security/   단일 관문
```

`contextIsolation: true`, `nodeIntegration: false`, 타입 지정 IPC 채널만 노출.
렌더러는 파일시스템에 직접 접근하지 않습니다.
**자동 업데이트·텔레메트리·크래시 리포터 없음.**
