# 로컬 LLM 으로 [LLM 위키에 묻기] 를 돌린다 — 검토

사내 PC 에 Ollama 와 Qwen2.5 가 깔렸다. 질의 한 가지만 로컬로 돌리는 구조를 본다.
같이 요청받은 하이브리드 검색(BM25 + 임베딩)도 여기서 다룬다. 둘은 한 덩어리다 —
로컬 모델을 쓰려면 검색이 먼저 있어야 한다.

**이 문서는 계획이고 구현이 아니다.** 재 보기 전에는 안 만든다 ([`CLAUDE.md`](../CLAUDE.md) §5).
§7 이 무엇을 재야 하는지 적는다.

이름 정정: 요청에 적힌 `BGM-m3` 는 **BGE-M3** 다 (BAAI General Embedding M3).

---

## 0. 결론

| 물음 | 답 |
|---|---|
| Ollama 를 질의에만 붙일 수 있나 | 있다. 다만 **네 번째 CLI 공급자로 넣으면 안 된다** |
| 어떻게 붙이나 | MCP 로 당겨 가게 하지 말고 **앱이 찾아서 프롬프트에 넣는다** |
| 하이브리드 검색이 필요한가 | 필요하다. 로컬 모델은 위키를 스스로 못 읽는다 |
| BM25 는 이미 있나 | 반쯤 있다. FTS5 가 계산하는데 **앱이 그 순위를 버리고 있다** (§3.1) |
| 벡터 데이터베이스가 필요한가 | **아니다.** 이 규모에서는 배열 하나로 끝난다 (§3.4) |
| 지금 만들어도 되나 | 아니다. 네 가지를 먼저 재야 한다 (§7) |

## 1. 지금 구조가 무엇을 전제하고 있나

[LLM 위키에 묻기] 는 `store.ask()` 다. 지금 이렇게 돈다.

```
질문 → CLI 를 띄운다 → CLI 가 앱의 내장 MCP 서버에 붙는다
     → 모델이 도구로 위키를 읽는다 → ANSWER_SCHEMA 로 답한다 → 관문
```

전제가 둘이다.

1. **공급자는 실행 파일이다.** `AgentCli` 는 `spawn` 으로 프로세스를 띄운다
   (`core/agent/exec.ts`). Ollama 는 `localhost:11434` 에 떠 있는 HTTP 서버다
2. **무엇을 읽을지 모델이 정한다.** 앱은 위키를 안 고르고 MCP 서버만 열어 준다.
   Claude Code 와 Gemini CLI 는 도구를 부르는 껍데기를 자기가 갖고 있다

Ollama 에는 그 껍데기가 없다. Qwen2.5 는 도구 호출을 지원하지만 **도구를 부르는 쪽은
클라이언트**다. 그 클라이언트를 우리가 써야 한다.

## 2. 두 갈래 — 어느 쪽으로 붙이나

### 2.1 에이전트 어댑터로 넣는다 (안 고른다)

`AgentCli` 를 하나 더 만들어 HTTP 로 말하게 한다. MCP 도구 호출 반복은 앱이 직접 돈다.

- 지금 Claude Code 와 Gemini CLI 가 공짜로 주던 것을 우리가 다시 쓰게 된다 —
  도구 목록 제시 · 호출 파싱 · 결과 되먹임 · 반복 종료 판정
- 작은 모델일수록 그 반복에서 헤맨다. 몇 바퀴를 돌지 예측이 안 된다
- 얻는 것이 없다. 우리 MCP 서버가 여는 도구는 위키 읽기 몇 개뿐이라
  **모델이 스스로 고를 여지가 애초에 크지 않다**

### 2.2 앱이 찾아서 넣는다 (이쪽)

```
질문 → 하이브리드 검색(BM25 + BGE-M3) → 상위 k 청크
     → 프롬프트에 넣어 Ollama 한 번 호출 → ANSWER_SCHEMA → 관문
```

- MCP 가 통째로 빠진다. 폴더 신뢰 문제와 무관해진다
- 호출이 한 번이다. 시간과 실패 지점이 예측된다
- 무엇을 모델에게 줬는지 앱이 안다. **관문 5(없는 앵커 인용)가 훨씬 좁게 판정된다** —
  준 청크에 없는 앵커는 지어낸 것이 확실하다
- 요청에 적힌 `BM25+BGE-M3 -> Qwen2.5 주입` 이 바로 이 구조다

한 가지를 잃는다. 모델이 "더 읽어야겠다" 를 못 한다. 검색이 처음에 못 찾은 것은
답에 못 들어간다. 그 대가로 예측 가능성을 얻는다.

## 3. 검색 구조

### 3.1 먼저 — 지금 검색은 순위를 버리고 있다

`core/search.ts` 의 `search()` 는 FTS5 에 `ORDER BY rank` 로 묻는다. FTS5 의 `rank` 는
BM25 다. **그런데 그 결과를 `Set<rowid>` 에 담고 `WHERE rowid IN (...)` 로 본문을 다시
읽는다.** SQL 의 `IN` 은 순서를 보장하지 않으므로 그 시점에 BM25 순위가 사라진다.

사람이 눈으로 훑는 화면에서는 티가 안 났다. **상위 k 개만 모델에게 주는 구조에서는
이것이 곧 품질이다.** 하이브리드를 얹기 전에 이것부터 고쳐야 한다.

### 3.2 무엇을 색인하나 — 위키다

지금 FTS 색인에 든 것은 **원본 청크**다 (`indexSource`). 위키는 색인돼 있지 않다.
[검색] 이 원본을 보고 [묻기] 가 위키를 보는 설계이기 때문이다.

로컬 질의는 위키를 봐야 한다. 그러니 **위키 페이지에 대한 색인이 새로 필요하다.**

- 자르는 단위: 페이지 안의 문단 묶음. 앵커 인용 `[^src-x#loc]` 을 자르는 지점 밖으로
  밀어내지 않는다. 인용이 청크에서 떨어져 나가면 모델이 출처를 못 붙인다
- front-matter 는 청크에 안 넣고 제목과 요약만 머리로 붙인다
- 페이지를 지우거나 고치면 그 페이지 청크만 다시 만든다 (`pageHash` 로 판정한다)

### 3.3 합치는 법 — RRF, 임계값을 만들지 않는다

BM25 점수와 코사인 유사도는 **단위가 다르다.** 정규화해서 가중합을 하려면 가중치와
임계값을 정해야 하는데, 이 프로젝트는 그렇게 들여온 상수에 두 번 데었다
([`CLAUDE.md`](../CLAUDE.md) §5 · §7 — Jaro-Winkler 0.92 가 한국어에서 오병합 3건,
엔트로피 게이트가 길이 하한 없이 뚫림).

그래서 **순위만 쓰는 RRF(Reciprocal Rank Fusion)** 로 합친다.

```
score(d) = 1/(k + rank_bm25(d)) + 1/(k + rank_dense(d)),  k = 60
```

- 점수 크기를 안 본다. 두 검색기의 단위 차이가 문제가 되지 않는다
- 조율할 상수가 `k` 하나다. 그것도 순위 감쇠 모양만 정한다
- 한쪽에만 걸린 문서도 살아남는다. 고유명사는 BM25 가, 바꿔 말한 질문은 임베딩이 잡는다

한국어에서 이게 맞는지도 재야 한다 (§7 의 W-O3). 다만 **틀렸을 때 고칠 손잡이가
하나뿐**이라는 점에서 가중합보다 안전하다.

### 3.4 벡터 저장소는 필요 없다

계산해 보면 답이 나온다. 위키 1,500장을 청크 5,000개로 잡는다.

| 항목 | 값 |
|---|---|
| BGE-M3 차원 | 1,024 |
| 벡터 하나 | 1,024 × 4바이트(Float32) = 4KB |
| 5,000 청크 전부 | **약 20MB** |
| 질의 한 번의 곱셈 | 5,000 × 1,024 = 512만 회 |

512만 회 곱셈-덧셈은 자바스크립트에서 한 자릿수 밀리초다. 5만 청크로 열 배가 돼도
200MB · 50밀리초 수준이다. **`sqlite-vec` 같은 네이티브 확장을 붙일 이유가 없다.**

이게 중요한 이유가 따로 있다. 사내 PC 는 설치 권한이 없다
([`docs/OFFLINE.md`](OFFLINE.md)). 네이티브 확장은 DLL 을 하나 더 들여야 하고
그 순간 포터블 exe 하나로 끝나던 배포가 깨진다. 벡터를 `.sb/embeddings.bin` 에
`Float32Array` 로 통째로 저장하고 켤 때 읽으면 된다.

## 4. 답변 형식 — 여기서는 Ollama 가 유리하다

Ollama 는 `format` 에 **JSON Schema 를 그대로 받는다**
([Ollama 문서](https://ollama.com/blog/structured-outputs)). 스키마를 서버가 강제한다.

지금 우리 공급자들과 견주면 이렇다.

| 공급자 | 스키마 강제 |
|---|---|
| Claude Code | `--json-schema` 로 강제. `structured_output` 이 이미 파싱돼 온다 |
| Gemini CLI | **못 한다** (`supportsSchema: false`). 프롬프트로 부탁하고 두 번까지 재요청한다 |
| Ollama | `format` 에 스키마를 넣는다 |

`ANSWER_SCHEMA` 를 그대로 넘길 수 있다. **모델이 작다는 것과 형식을 못 맞춘다는 것은
다른 문제**다. 형식 쪽은 서버가 해결해 준다. 남는 위험은 내용이다 — 준 청크에
없는 말을 지어내는 것. 그건 관문 5 가 잡는다.

## 5. 라우팅에 어떻게 들어가나

**공급자 목록에 넷째로 넣지 않는다.** `PROVIDERS` 는 "예산을 쓰는 외부 CLI" 의 목록이고
`route()` 는 상한과 MCP 가능 여부로 고른다. Ollama 는 둘 다 해당이 없다.

별개의 축으로 둔다.

```
설정 → [LLM 위키에 묻기] 를 무엇으로 답할까
        ( ) 지금 고른 CLI (claude-code / gemini)
        ( ) 로컬 모델 (Ollama)          ← 검색 후 주입
```

- `store.ask()` 안에서 갈라진다. 로컬이면 `askLocal()` 로 가고 MCP 를 안 띄운다
- 지출 계량기에 0 을 더한다. 돈이 안 드는 것과 안 쓴 것을 구별해야 한다
- 위키 갱신(ChangeSet)은 **안 준다.** 그쪽은 파일을 쓰는 제안이고 관문 아홉을 다
  통과해야 한다. 작은 모델로 먼저 시험할 자리가 아니다

## 6. 덤으로 얻는 것 — 등급 라우팅

지금 열람 등급은 넷이다 (`public` / `internal` / `confidential` / `restricted`).
등급이 있어도 **질의는 지금 전부 외부 CLI 를 탄다.**

로컬 경로가 생기면 규칙 하나를 세울 수 있다.

> `confidential` · `restricted` 를 인용한 페이지가 걸린 질의는 로컬 모델로만 답한다.

속도 문제가 아니다. 설계 이득이다. 지금은 "그 문서는 묻지 마십시오" 가 유일한 답인데
그건 사람이 지켜야 하는 규칙이다. 사람이 지키는 규칙은 곧 잊힌다.

## 7. 만들기 전에 재야 하는 것 넷

전부 사내 PC 에서 돈다. 합성 한국어 입력만 쓰고 **사내 문서를 안 읽고 안 내보낸다.**
스크립트는 [`spikes/local/ollama-check.mjs`](../spikes/local/ollama-check.mjs) 다.

| 번호 | 무엇을 | 통과 기준 |
|---|---|---|
| W-O1 | 두 모델이 깔려 있나. Qwen2.5 판과 크기 | 목록에 뜬다 |
| W-O2 | BGE-M3 임베딩 차원과 속도 | 1,024 차원 · 청크당 시간을 기록 |
| W-O3 | Qwen2.5 가 `ANSWER_SCHEMA` 를 맞추나 | n=5 에서 유효 JSON 5/5 |
| W-O4 | 준 청크에 없는 앵커를 지어내나 | 지어낸 인용 0건 |

W-O2 가 제일 중요하다. **처음 색인을 만드는 시간이 전부 여기서 나온다.** 청크당
100밀리초면 5,000 청크가 8분이고 한 번만 하면 된다. 청크당 1초면 83분이라 다른
설계가 필요하다. 지금은 모른다.

W-O3 이 5/5 가 아니면 §4 의 전제가 깨진다. 그때는 이 계획을 접는 편이 낫다.

## 8. 안 하는 것

- **위키 갱신을 로컬로 돌리지 않는다.** ChangeSet 은 디스크를 고치는 제안이다
- **원본 검색을 안 건드린다.** 지금 FTS 검색은 사람이 쓰는 도구이고 잘 돌고 있다.
  §3.1 의 순위 보존만 고친다
- **임베딩을 클라우드로 안 보낸다.** 사내 문서가 그대로 나간다
- **모델을 저장소에 안 넣는다.** BGE-M3 가 567MB 다. `ollama pull` 로 받는다
